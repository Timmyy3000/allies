# Gmail attachment retrieval

Route: fast. HTML required: no. Status: revised for review. Revision: 2.

## Outcome and scope

An Ally can discover certificate PDFs in a connected Gmail message, retrieve selected attachments, and return real private downloadable links. Cloud owns Gmail credentials, live grants, storage and product files; Foundry remains a credential-free JSON relay. Preserve existing search/get text, organizing and send confirmation behavior.

Publish unchanged provider attachments directly in Cloud through the existing `reserve_publication`, `receive_publication_file`, inspection and `publication_view` services. The existing reply sanitizer accepts only ready publications scoped to the dispatch message/binding, and private file access checks ownership and tenant ancestry. No new endpoint, table, migration, dependency, public URL, binary relay or frontend change is needed.

Alternative considered: download into Hermes then `publish_files`. That requires increasing both 64 KiB relay limits or adding a binary transport, safe workspace writes and another upload. This task only returns unchanged PDFs; runtime retention for runtime-created working files does not require this copy. Runtime attachment editing/combining is outside scope.

## Contract and safeguards

- `get(message_id)` adds `attachments`, each containing `part_id`, bounded/sanitized display `filename`, `mime_type`, decoded `size`, and whether download is supported. Walk nested MIME parts including inline body data; return no attachment bytes or provider attachment IDs. Keep text/body/truncation fields. Bound traversal to 256 parts, depth 20, and metadata to 50 attachments; expose an explicit truncation flag rather than silently losing entries. Keep the JSON result below the existing 64 KiB relay envelope. Exclude filename-bearing or attachment-disposition text parts from the message body. Decode only a separately bounded prefix of the selected body text sufficient for the existing 12,000-character output plus truncation evidence; never decode a large text attachment as body.
- `download_attachment(message_id, part_id)` accepts a message ID and bounded part ID (including the empty root part ID), never a caller-supplied attachment ID, URL, filename, size or MIME type. Re-fetch the message and resolve exactly one real attachment part. Retrieve external bodies from Gmail's attachments API; decode inline bodies in Cloud. Apply the existing file type/filename rules; PDF is required. Report unsupported types without publishing them. Treat provider metadata as untrusted.
- Every new action requires current connection and `gmail get` grant plus the existing turn/binding/fingerprint authorization. Perform these checks before any ready/replayed publication result. Grant revocation blocks status as well as retrieval; it does not change the independent owner access contract for an already published product file. Cross-workspace, cross-Ally, other-message and stale binding references fail closed.
- Bound decoded bytes to the existing 25,000,000-byte file maximum, enforce metadata size against actual decoded length, strictly validate base64url, and compute SHA-256 from bytes. Provider reads must use limit+1 and explicitly reject overflow; `_gmail` currently reads 5,000,001 bytes without rejecting overflow. Retain the ordinary 5 MB cap for unrelated calls; use an explicit 34,000,000-byte cap for `get` full-message discovery and download full-message/attachment reads, sufficient for one maximum-sized inline attachment plus JSON overhead. Larger composite messages fail with an actionable size error. Keep the current eight-second provider timeout and at most one message plus one attachment request per download. No implicit download batch or unbounded polling.
- Derive a deterministic publication UUID and source-version UUID from a versioned namespace plus dispatch message ID, Gmail message ID and part ID. Retries and new tool call IDs within the same turn reuse the publication. Manifest digest also binds sanitized name, size and content hash; changed provider bytes conflict rather than overwrite. Existing quota limits enforce 10 returned files and 50,000,000 total bytes per reply.
- Reserve using the resolved binding/message, upload verified bytes from a bounded in-memory stream, and keep the existing inspection queue/recovery, storage accounting, write fences, generation and deletion controls. Never report ready based only on successful provider fetch/upload. A repeated ready/validating publication returns its state without duplicate uploads. Concurrent active upload returns a safe pending/conflict result. If storage fails, retain existing recoverable state; retry a pending or expired receiving file using its current revision/generation, never replace an immutable/rejected file or bypass cleanup. Do not place Gmail bytes in `IntegrationToolCall.response` or task payloads.
- `attachment_status(publication_id)` uses the same live Gmail read checks and `publication_view(binding_id, message_id)`. Long-poll pending state for at most 20 seconds with one-second database reads, no locks held across waits, within the existing 25-second relay timeout. Re-check current connection, live grant and scoped publication before returning after waiting. Return compact `publication_id`, state, filename and a ready-only `chat_reference` such as `[certificate.pdf](/files/<id>)`; safely escape the label. Download returns the same compact shape without a second long-poll budget. At most five status calls per turn; if still pending, preserve the publication ID in the receipt and explain that retrieval succeeded and inspection is pending, never that Gmail cannot retrieve attachments. Failed/rejected states contain safe actionable errors and never a link. No raw provider data, private storage URL, base64, credential, customer document or content-bearing exception is logged or returned to Hermes.
- Foundry's schema/instructions expose both actions and `part_id`/`publication_id`: search, get attachments, download selected parts, check pending status, then include only returned `chat_reference` in the answer. Never claim a PDF was returned before ready. Keep transport limits, retry identity, redirect rejection and lease authorization unchanged.

## Risks, rollback and decisions

- Parent confirmed the reported production Ally and matching reply. The managed Gmail gap matches the report. Private conversation context remains in episode evidence, not public Foundry documentation. Older Gmail handoff is superseded by the current merged episode.
- Provider JSON/base64 buffers amplify memory use; the explicit 34 MB response cap bounds each request but does not provide streaming decode. Keep one attachment per action, no parallel attachment batch. Revisit streaming only after a demonstrated memory problem.
- Inspection is asynchronous. Worker/beat/private storage and inspection must be healthy; a pending file is an honest incomplete result. Existing file retry state was designed for Foundry-returned files: this fix must not pretend that a Gmail publication has a Foundry frozen source. Tests must show pending/expired upload recovery through a repeated download action, and return an explicit failure for terminal rejection. A new generic retry worker is outside scope.
- Direct publication is an intentional exception to using runtime `publish_files` for runtime-created artifacts, not a replacement for that flow. Parent supplied canonical Nabu ownership context; its exact note revision remains in the parent's evidence record.
- Rollback Foundry schema/instructions first, then Cloud new actions. Keep existing published files and their lifecycle; no migration rollback or file deletion. If emergency capability disable is needed, use existing Gmail disable controls, acknowledging they disable all managed Gmail operations.
- No unresolved product decision blocks implementation. Numeric traversal/envelope bounds are implementation defaults to verify with fixtures and policy review; do not silently raise the ordinary relay cap.
