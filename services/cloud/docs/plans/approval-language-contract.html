Feature Overview

Cloud must explain an approval in ordinary language and tell the Interface exactly when the user's choice is saved. The existing implementation already saves the first decision transactionally, schedules delivery after commit, enforces deadlines, and verifies the Foundry receipt. Preserve those mechanisms.

Today, activities/presentation.py exposes the stored technical label and preview in the authorized detail response. Approval response statuses are unrestricted strings, and list responses already retain message_id. There is no persisted explanatory summary. The literal phrase "runtime blocked" was not found in Cloud backend source; the actionable Cloud boundary is the approval/detail and awaiting-action presentation. Do not claim to fix a phrase generated by Hermes or hardcoded in Interface through a speculative Cloud rewrite.

This plan serves people deciding whether their Ally may continue, Interface engineers implementing AT-029, and operators diagnosing failed explanation or delivery. A scoped detail response must carry understandable, request-bound copy and separate complete forced-redacted details. It must distinguish a committed choice from later execution confirmation.

User Stories

  1. As a person reviewing an approval, I can understand the proposed action, target, effect, and reason before opening technical details.
  2. As a person submitting a choice, I see that it was saved even while the Ally's confirmation remains pending, and an exact retry cannot create another choice.
  3. As an operator, I can distinguish provider fallback, invalid output, and delivery uncertainty without logging commands, arguments, private values, or generated text.

Service Primitives

Canonical input identity (ADV-004): use the existing gateway canonical_fingerprint/canonical_json_bytes convention over exactly {"approval_request_id":"<canonical UUID>","preview_digest":"sha256:<hex>","action_kind":"<allowlisted kind>","policy_version":"approval-explanation.v1"}. Persist the resulting canonical-json-sha256:v1:<64 lowercase hex> as input_fingerprint inside the JSON projection, together with these exact components. The policy version changes whenever prompt, sanitizer or output-policy semantics change. Recompute from the current row before accepting cached copy, before sending, and before completion. CAS requires both the exact claimed fallback object and its input_fingerprint, plus matching current request UUID, action kind and exact preview bytes; no hash alone substitutes for tenant scope. Provider output must echo the expected fingerprint. Old JSON without the fingerprint or with mismatching components is invalid, becomes bound fallback, and does not trigger automatic regeneration. The additive migration leaves existing rows as {}; it performs no provider work.

The authorized detail flow first obtains the existing scoped approval. In a short transaction, if explanation={}, store the deterministic fallback bound to the immutable request/digest and return a local winner flag. A conditional update makes concurrent readers losers; they immediately use the stored fallback. Commit before starting I/O. The winner checks the dedicated enable gate and acquires the bounded tenant/global budgets below before any provider call. It makes at most one provider call, then validates, reauthorizes, recomputes the input fingerprint, and conditionally replaces the exact claimed fallback object. Disabled or exhausted paths retain deterministic fallback. Return freshly scoped and reconciled state. No model result can overwrite a changed binding, later policy object, or another generated result.

A crash after the claim leaves fallback durable. Do not automatically retry generation on refresh or process restart; the claim is the per-request budget. Existing rows generate only when opened and eligible. Terminal/expired approvals and missing configuration use fallback without provider work. A changed/invalid stored explanation is ignored and replaced with current deterministic fallback, not blindly reused or automatically regenerated.

The POST path must never call the provider. If no explanation has been stored, its serializer returns validated deterministic copy without changing generation ownership. Network latency cannot hold the decision lock or delay a committed choice.

Plain-language glossary

A model/table is durable database state. A schema/DTO validates data crossing a boundary. An enum is the allowed vocabulary. A service primitive owns one operation. A digest identifies exact preview bytes; it is not a permission. Decision recorded means the choice is saved in Cloud. Confirmation means the matching runtime request reported its result. No new index is needed because reads use the existing approval key and scoped list queries.
