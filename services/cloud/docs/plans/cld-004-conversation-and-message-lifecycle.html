Implementation plan

One durable conversation per Ally, one accepted intent per send key.

Cloud becomes the product-truth boundary for conversation identity, ordered message records, Workspace authorization, bounded history, and exactly-once text acceptance. Downstream execution remains a later contract.

Decision view

Build a compact chat app with additive models and routes. Lock the conversation for identity and sequence allocation, fingerprint normalized text for retries, and commit before responding. Keep Foundry, Hermes, Fly, streaming, replay, stop, and retry outside this ticket.

What changes and what stays outside

Cloud owns

  • One default Conversation per Ally, public IDs, ordered Message records, customer-visible status, content, and idempotency.
  • Workspace capability checks on every read and mutation, including duplicate lookup.
  • Text-only acceptance beginning at queued, bounded pending work, and opaque-cursor history.
  • Product-only response/error vocabulary and the nullable execution projection seam.
  • Queue invariant: one active send-origin user row in in_progress plus at most 20 queued send-origin rows. Imported onboarding rows are completed history and do not count.
  • Conversation Workspace authority is derived through Ally.workspace, not duplicated on Conversation.
  • The sole low-level transition primitives and tests: claim_next_turn for queued → in_progress and complete_turn for active → terminal.
  • Database foreign keys, uniqueness/check constraints, migration validation, and route-level authorization/privacy tests protect the fresh Alpha chat tables; no custom runtime switch or ancestry validation job is introduced.

Later owners

  • CLD-005 owns caller/orchestration, Foundry execution dispatch, and execution projection population. It must call the CLD-004 transition primitives with no pre-lock or surrounding Conversation transaction; each primitive is the sole lock owner, and CLD-005 must not duplicate them.
  • CLD-006 owns replay, reconnect continuation, streaming, stop, retry, and terminal recovery.
  • Interface owns drafts, loading/error copy, responsive composition, and mapping product status to presentation.
  • Attachments, editing/deletion, routines, approvals, and cross-Ally feeds remain out of scope.

Lifecycle and ownership

This flow answers how a send becomes durable without implying that downstream execution has started.

flowchart LR A[Authenticated Workspace user] --> B[Resolve Ally or Conversation] B --> C{Current capability?} C -- no --> D[Privacy-safe 404] C -- yes --> E[Lock conversation] E --> F{Existing key?} F -- same fingerprint --> G[Replay original message] F -- different fingerprint --> H[409 conflict] F -- none --> I{Pending queue below 20?} I -- no --> J[429 queue full] I -- yes --> K[Allocate sequence and insert queued message] K --> L[Commit before success] L --> M[201 accepted message] M -. later contract .-> N[CLD-005 execution projection]

Queue invariantA Conversation has zero or one active send-origin user Message in in_progress, identified by that message ID, and up to 20 send-origin user Messages in queued. CLD-003 greeting and reply rows are completed historical onboarding rows and are excluded. Duplicate replay is checked before capacity and still succeeds when full. CLD-004 owns the sole claim_next_turn transition queued → in_progress and complete_turn transition active → terminal; CLD-005 calls them with no pre-lock or surrounding Conversation transaction because each primitive owns the Conversation lock, without duplicate lifecycle SQL. A same-status complete_turn retry returns the unchanged terminal row; a different terminal status conflicts. Only the active row may transition to a terminal state.

User journey

  1. Authenticated person opens a Workspace-owned Ally.
  2. Cloud resolves the one continuing conversation and bounded newest history, including onboarding greeting and reply when present.
  3. If the CLD-003 handoff is missing, invalid, or partial, Cloud returns typed onboarding_handoff_repair_required or onboarding_handoff_unavailable; it does not fabricate, duplicate, or report success, and no pending capacity is consumed.
  4. An unsent draft remains client/session state.
  5. Interface sends text with a fresh caller retry identity.
  6. Cloud validates authority and input, commits one queued Message, and returns stable product representation.
  7. The accepted message remains visible through waking, queueing, browser disconnect, and downstream delay while execution projection is null/delayed. External downstream failure-injection evidence belongs to CLD-005.
  8. Same key/content returns the original result; changed content conflicts.
  9. Returning later reads the same ordered history. Another Workspace cannot infer the resource.

Abuse and boundary guardrails

Per-user/workspace send limit

New sends lock Conversation, check the duplicate key, then use the existing cache-backed auths.throttle.check_rate_limit exactly once with scope="chat-send", identity=f"{workspace_id}:{user_id}", and a deterministic HMAC request marker. The default is 30 new sends per rolling 600 seconds, configurable to 1..120 and 60..3600. The helper owns HMAC/key construction and idempotent request-marker/count handling; rollback clears only the deterministic request marker and retains the attempted aggregate quota count until the normal window expires (fail closed), it never decrements a shared bucket; replays are checked first and do not consume allowance; cache outage fails closed.

The two domain reasons are conversation_queue_full and send_rate_limited, but both map to this exact public 429 body for every caller: {"status":"error","message":"Request temporarily unavailable","error":{"code":"rate_limited"}}. No remaining count, reset time, identity, key, content, Retry-After, or timing detail appears in body or headers. Rate-limit wide events, logs, and metrics are aggregate-only: schema version, event, allowlisted route ID, method, status 429, and reason. They suppress duration, request/correlation IDs, identity, key, content, allowance, reset time, and other request-derived fields. Tests inspect all three payloads, assert no duration_ms, prove the 31st default-window send is a privacy-safe 429, another workspace has an independent bucket, and duplicate replay bypasses the counter. A PostgreSQL barrier test proves identical concurrent sends produce one row and one limiter increment.

Database and route boundaries

Fresh Alpha chat tables rely on ordinary foreign keys, uniqueness/check constraints, and additive migration validation. Route-level tests cover mismatched Workspace and foreign Conversation/Ally IDs as privacy-safe 404s; no separate ancestry job, persisted route switch, readiness state, report, or quarantine model is introduced.

Plain-language glossary

  • Model / table: persisted database record and its storage table.
  • Schema: validated input/output boundary, not automatically a table.
  • Enum: closed list of allowed named values.
  • DTO: data-transfer object across a boundary; it need not be persisted.
  • Primitive: small service operation owning one state transition or durable boundary.
  • Index: database access structure for a known lookup/order pattern.
  • Constraint: database/application rule rejecting invalid combinations or transitions.
  • Invariant: condition that stays true across retries, concurrency, failures, and migrations.

Rollout, decisions, and evidence

Rollout

  1. Apply additive chat migration in staging; verify fresh PostgreSQL migration and migrate --check. Verify fresh PostgreSQL migration, migrate --check, and foreign-key/uniqueness/check constraints before normal route rollout.
  2. Deploy cursor verification with both the current signing key and the next key's verifier available, while issuance still uses the current key; record the cursor TTL and overlap window (at least TTL plus bounded skew/rollout buffer).
  3. Switch the active signing key for new cursors only after the verifier is deployed; monitor old-key acceptance and new-key issuance without logging cursor contents.
  4. Keep the previous verifier until every cursor signed by it is outside the TTL/overlap window, then retire it and confirm post-window old-key rejection. If the new key is faulty, roll issuance back to the previous key while both verifiers remain active; never delete or rewrite cursor/history data.
  5. After migration and route-level authorization/privacy checks pass, exercise onboarding/history/cursor evidence and typed repairable/unavailable handoffs without fabricating success.

Decisions

  • Dedicated chat app; conditional default per Ally; conversation ID is message-operation boundary.
  • Conversation-scoped HMAC key and normalized fingerprint; duplicate checks after authorization.
  • One lifecycle enum starts at queued. Pending means 20 queued send-origin rows (configurable 1..100) plus one active in_progress row; CLD-004 owns the sole transition primitives/tests, each with its own short transaction and Conversation lock. CLD-005 calls them with no pre-lock or surrounding transaction. Imported onboarding rows are completed and excluded.
  • Identical sends serialize on Conversation: duplicate lookup precedes the limiter; the winner uses one deterministic HMAC request marker and cache-helper marker/count handling, while the loser replays without a limiter call. On transaction failure, rollback clears only the request marker and retains the attempted aggregate quota count until the normal window expires (fail closed), it never decrements a shared bucket. PostgreSQL proves one row and exactly one increment.
  • History default 50/max 100; opaque HMAC cursor with schema version, key ID/version, expiry, conversation scope, and exclusive sequence. New cursors use the active key; the previous key remains accepted for at least the cursor TTL plus bounded rollout buffer, then is retired and rejected.
  • Conversation derives Workspace through Ally.workspace; DB FKs and uniqueness/check constraints protect the fresh Alpha schema, with route-level mismatch/foreign-resource 404s and no custom ancestry job or quarantine destination/model.
  • No persisted route switch, readiness state, custom ancestry job, or report is introduced; ordinary constraints, migrations, and route-level tests are the Alpha safeguard.
  • Rate-limit observability is aggregate-only: schema version, event, allowlisted route ID, method, status 429, and reason conversation_queue_full or send_rate_limited; duration and request-derived fields are suppressed.
  • Generic API exception logging resolves an allowlisted route ID/template (never request.path/query) and records only method/status, stable class/safe fingerprint, and content-free correlation metadata; no traceback, exception string, body, Idempotency-Key, SQL, provider data, or raw path.
  • Missing/invalid/partial CLD-003 handoff yields typed repairable/unavailable with no fabrication, duplication, success, or capacity impact.
  • Alpha text-only; no new worker/outbox/gateway/event system in CLD-004.
