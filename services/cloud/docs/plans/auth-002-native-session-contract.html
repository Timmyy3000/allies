The handoff in one flow

Cloud remains the confidential Google relying party. Mobile is a public Cloud client and proves possession of its PKCE verifier when it redeems the one-time Cloud code.

1. StartMobile sends an exact redirect URI, state, and PKCE S256 challenge.
2. BrowserCloud returns an authorization URL for the external system browser.
3. GoogleGoogle returns to Cloud's exact HTTPS callback, not to the app.
4. VerifyCloud checks provider state, nonce, issuer, audience, and claims.
5. ReturnCloud redirects to the exact app URI with code and app state only.
6. ExchangeMobile sends the code, verifier, and redirect URI; Cloud issues tokens.
7. OperateAccess stays in memory; the opaque refresh credential rotates in SecureStore.

What changes, and what stays out

AUTH-002 extends the implemented AUTH-001 account and session foundation. It does not replace browser auth or pull Foundry into the account-access boundary.

Included

  • Google through the external system browser.
  • Authorization code with PKCE S256 and exact redirect allowlisting.
  • Short-lived, single-use hashed Cloud exchange code.
  • Short-lived bearer access JWT and rotating opaque refresh credential.
  • Refresh hashing, one-winner rotation, reuse detection, family revocation, expiry, logout, rate limits, audit, redaction, migrations, OpenAPI, and tests.
  • Published Cloud contract and Interface consumer handoff.

Excluded

  • Foundry, Hermes, Fly, Ally, runtime, execution, gateway, conversation, and managed conversation.
  • Pre-auth state, account claims, waitlist changes, or pre-auth Ally transfer.
  • Google tokens in Interface, client secrets in the app, embedded WebViews, and browser-cookie copying.
  • Attestation, DPoP, mTLS, MFA, passkeys, biometrics, push approval, account linking UI, and remote session-list UI.
  • Mobile implementation itself; that is INT-008 after this contract is accepted and published.
Foundry dependency result. AUTH-002 has no Foundry dependency. A required branch-diff check rejects new Foundry, Hermes, Fly, Ally-runtime, or runtime-service imports, packages, settings, jobs, routes, and deployment changes.

Security and data invariants

The implementation extends existing session services instead of creating a parallel token system.

Redirect boundary

Exact URI matching rejects query, fragment, wildcard, user-info, and prefix tricks. Production claimed HTTPS links are preferred. Google always returns to a Cloud-owned callback.

One-time values

Native transactions and exchange codes store digests or sealed values, expire quickly, and are consumed under a row lock. Provider and app tokens never appear in redirect URLs or logs.

Session boundary

A closed client_kind distinguishes browser and native families. Bearer requests cannot use browser families, and browser cookies cannot use native families.

Refresh boundary

Refresh credentials are opaque and hashed. Rotation is one-winner. Reuse revokes the family. Interface serializes refresh and never retries an old token.

Persistence boundary

Mobile stores only the opaque refresh credential in Expo SecureStore. Access stays in memory. Zustand, TanStack Query, AsyncStorage, analytics, and ordinary files hold no credential.

Operational boundary

Audit events use low-cardinality opaque references. No raw code, token, email, provider claim, redirect query, full IP, request body, or provider response enters logs or analytics.

Railway identity must be proved before enablement

The proposed native requester identity is Railway's edge-provided X-Real-IP, normalized to IPv4 /24 or IPv6 /64 and HMACed before shared Redis. Client-selected identifiers never contribute.

Bearer allowlist

GET /auths/me, PATCH /auths/me/profile, the four reviewed avatar operations, and GET /workspaces/{workspace_id}. New routes are denied until reviewed.

Public exclusions

Native begin, callback, exchange, and refresh; all browser auth; waitlist; health; OpenAPI; Google; app-return links; and direct avatar uploads. Native logout handles its optional bearer explicitly.

The Interface-owned native-session-contract.test.ts compiles the four new native-session methods, captures the existing account-method bearer allowlist separately, proves snake-case mappings, and table-tests every error state, including refresh reuse and logout uncertainty.

Forward upgrade is separate evidence

The migration test starts from the current pre-AUTH-002 leaf, auths.0002_externalidentity_email_verification. Fresh migration application does not satisfy this gate.

Seed and migrate

Create a user, one browser-era family, and one unused refresh row with a known token digest. Migrate once from the current pre-AUTH-002 leaf to the AUTH-002 leaf, then restore the graph in finally. Normal migration checks cover repeat application.

Assert and rotate

Assert client_kind=browser, native schema availability, existing browser access, successful refresh rotation in the same family, and the current reuse regression on SQLite and PostgreSQL.
