# CLD-012 independent plan review

## Verdict

Needs revision before Luna implementation.

## Actionable findings

| ID | Severity | Area | Exact evidence | Impact | Confidence | Required plan change |
| --- | --- | --- | --- | --- | --- | --- |
| SOL-001 | P1 | Approval authorization race | `docs/plans/cld-012-routines-contract.md:120-123,141,153,234` says Foundry is authoritative and that approval, cancellation, and expiry serialize there, but it does not define which durable timestamp/clock creates the 24-hour expiry or require one atomic compare-and-set that both consumes approval authority and transitions the run into action execution. Current Foundry validates caller-carried `expires_at` against its own clock (`backend/runtime/services/approvals.py:99-103,196-215,442-453`) and currently caps approval lifetime at 300 seconds (`backend/runtime/contracts.py:32,302-317`). | With clock skew, delayed delivery, or concurrent approval/cancel requests, an expired or replaced decision could still authorize an action, or a valid decision could be rejected inconsistently. Saying the winner is serialized is not enough to make the winner deterministic or fenced. | High | Amend the freeze matrix and fixtures to name Foundry's durable approval-request creation/expiry record and clock as authoritative; define the exact CAS preconditions and terminal outcomes for `pending -> authorizing/working`, `pending -> rejected`, `pending -> expired`, and `pending -> cancelled`; require that generation fencing and permission consumption occur in the same transaction; and add boundary vectors for equality, delayed commands, duplicate decisions, and cancel/approve races. Keep the 60-second transport deadline separate. |
| SOL-002 | P1 | Routine mutation versus occurrence admission | `docs/plans/cld-012-routines-contract.md:113-125,139-153,230-235` covers future-only edits, deletion, pause, snapshots, and occurrence uniqueness independently, but never defines the linearization point or winner when create/update/pause/delete races with scheduler admission of a due occurrence. | CLD-013 and FND-012 can make incompatible choices: a run may start after deletion/pause, an update may partly affect an admitted run, or retries may create different snapshots for one occurrence. That violates deletion/pause guarantees and preservation of active-run context. | High | Add an explicit Cloud atomic admission contract: lock/CAS the routine revision and scheduling state while creating the unique occurrence and immutable run snapshot. Specify outcomes for delete-vs-due, pause-vs-due, update-vs-due, duplicate scheduler claims, and delete/pause after admission. Freeze whether admission winning makes the run “already active” for product semantics, and add executable race vectors for each winner. |
| SOL-003 | P1 | Feasibility evidence honesty | `docs/plans/cld-012-routines-contract.md:180-190,212,270-276` proposes an offline `docker run --network none` standalone script, while line 276 admits that this cannot prove real model/tool execution responsiveness and leaves the real Hermes endpoint command to be determined later. Acceptance criterion 4 nevertheless allows a generic “pinned-runtime proof” to satisfy responsiveness, history attribution, memory continuity, and file safety. | Luna could produce a passing provider/identifier smoke test and have it read as the ticket's required concurrent-session demonstration even though no actual Hermes worker/session executed concurrently. This would falsely unblock FND-012. | High | Split Phase 2 and acceptance into two named evidence classes: (a) offline provider/storage diagnostics and (b) an actual pinned Hermes service/worker concurrent-session probe. Record the exact service entrypoint, model transport, readiness check, bounded credentials/configuration, and assertions before implementation. State that class (a) can only identify provider capabilities; CLD-012 remains incomplete and dependent integration blocked unless class (b) runs successfully or produces a reproducible failure proving the required Foundry change. |
| SOL-004 | P2 | Fixture test oracle | `docs/plans/cld-012-routines-contract.md:175-178,209-210,230-235` requires positive and negative vectors for closed schemas, bounds, authorization, state transitions, and race outcomes, but also forbids runtime DTO/handler changes and says tests only reuse canonical serialization/fingerprint helpers. A JSON fixture plus hash helper cannot reject unknown fields, enforce per-operation omission/null rules, authorize owners, or execute state transitions. | Tests may pass while the purported contract is internally incomplete or contradictory, creating false compatibility evidence across Cloud and Foundry. | High | Narrow the CLD-012 executable claim. Make fixture tests prove only byte-identical fixture revision/hash, canonical serialization, fingerprint compatibility, and structurally complete case metadata. Require each negative/race vector to declare the future enforcing owner and expected stable result code, and hand those vectors to CLD-013/FND-012 as mandatory executable acceptance tests. If Luna is instead expected to execute schema validation now, explicitly authorize and name a minimal typed contract validator in scope; do not imply documentation vectors are an implementation oracle. |
| SOL-005 | P2 | Contract ownership and drift | `docs/plans/cld-012-routines-contract.md:68-70,176-178,194-205` calls the Cloud document canonical and creates a compatibility copy and fixtures in Foundry, but it does not define the version identity fields, byte-level canonical artifact, update workflow, or a deterministic check that prevents the two repositories from publishing divergent `routines-v1` content under the same name. | Cross-repository consumers can appear compatible while referring to different prose/schema revisions or fixture sets, especially when PRs merge independently. | Medium-high | Define one normative artifact owner and identity tuple (contract name, schema version, content revision/hash, fixture hash). Make the Foundry copy explicitly vendored/non-authoritative, require byte-identical fixture content or a documented generated subset, and specify merge order plus the check each repository runs against the accepted hashes. Avoid adding a registry or shared package. |

## Disposition recommendation

Revise the plan and re-run independent review. Do not start Luna implementation until SOL-001 through SOL-003 are resolved in the plan; SOL-004 and SOL-005 should also be incorporated to keep the contract evidence minimal and honest.
