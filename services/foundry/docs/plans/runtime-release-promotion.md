# Runtime release promotion

Status: accepted for implementation under existing owner authorization. Revision: 1 (2026-09-15).
Route: fast. HTML required: no. Reviews: ADV-001–003 and SIM-001–005 accepted and incorporated.

## Outcome and boundaries

Replace the combined image workflow with PR validation, manual publication to staging, and later manual production promotion by explicit release ID without rebuilding. Staging may advance independently; selecting a prior compatible release is rollback. Preserve all smokes, provenance/SBOM, immutable digest pairs, write-once durable evidence, atomic paired desired configuration and readback.

The current workflow rebuilds after smoke tests and can update production directly. Remove that option. Existing application branch-promotion/release workflows remain unchanged; runtime IDs use `runtime-<run_id>` and cannot trigger their `v*` tags. No runtime/backend lifecycle change, fleet rollout, live deployment, merge, new signing system, generic deployment framework, or repository governance changes are authorized here.

## Workflow contracts

- `.github/workflows/hermes-image.yml`: PR-only, read-only contents, no deployment/package-write credentials; build/test both local images and retain provenance/SBOM OCI output. Paths cover `runtime/**`, release/integration/smoke scripts and their tests, three image workflows, and Makefile. Retain normal CI/security/review gates.
- `.github/workflows/runtime-publish.yml`: manual dispatch on `refs/heads/dev` only, checkout fixed dispatch SHA, no source/resume input. Generate `runtime-<run_id>`. One publishing concurrency group, `cancel-in-progress: false`, spans build through final release. Grant package/release writes only where used. Stage only after exact-digest smoke success and durable candidate persistence.
- `.github/workflows/runtime-promote.yml`: manual dispatch on `dev`, required `release_id`, no latest/current-staging fallback. One production job validates immediately before mutation under one production concurrency group, `cancel-in-progress: false`. Checkout dispatch SHA for trusted tooling; never checkout release-controlled code. No build steps or package-write permission.
- Bind deployment jobs to existing `foundry / staging` and `foundry / prod` environments. `dev` is not protected and these environments have no protection rules. Existing repository writers/manual dispatch authority are trusted; do not invent ancestry checks, approval gates, or a mandatory protection project. Inputs/assets are data; use argument arrays or environment variables, never shell interpolation.

## Image and durable evidence contracts

Build each published image once for `linux/amd64` with provenance and SBOM, push unique candidate tags, capture the OCI index digest, and pull/run the complete smoke suite using those two digest references. Verify the platform image and supplied attestation subjects belong to that exact index; check provenance source SHA against the recorded checkout where emitted. Ensure the build supplies source metadata and reject absent/inconsistent required subject/source evidence. Preserve unsigned BuildKit provenance/SBOM inside the index; this proves consistency within the trusted publisher boundary, not cryptographic builder identity. Never rely on arbitrary attestation URLs.

Use GitHub Releases, with two small create-only JSON assets (maximum 64 KiB each) rather than another persistence service:

- `candidate.json` on a draft release: schema version 1, release ID, repository, full source SHA, workflow/run ID/attempt for audit, platform, both allowlisted `repository@sha256:<64 lowercase hex>` refs, exact OCI attestation identities, and successful validation outcome. Tag resolves exactly to source SHA. Write/read back the candidate only after digest smokes pass; it is the recovery checkpoint before staging mutation.
- `release.json`: candidate identity/pair plus historical staging evidence (`desired_config_verified`, exact readback pair, timestamp, run ID/attempt, `machine_adoption: not_verified`). Upload/read back, then publish the draft. A finalized release is eligible only with matching tag/source, repository, schema, pair, validation success and staging evidence. The durable final record owns those outcomes; no historical workflow-run API queries or replayed smoke matrix during promotion.

Fetch by exact ID through this repository's release API. Reject draft promotion, missing/duplicate assets or JSON keys, unsupported schema, oversized/malformed fields, wrong repository/image namespace, missing images/attestations, digest/platform/source inconsistencies, and staging-pair mismatch before any configuration write. Source/run fields remain audit evidence. Never update existing assets/tags: reuse only after validating identity/content equality. GitHub immutable releases are disabled; workflow write-once policy trusts repository maintainers, who can still alter assets outside the workflow. No new signing infrastructure or settings mutation is needed.

## Configuration and recovery

Keep Railway optional and isolated in one concrete command, `scripts/integrations/railway/update_runtime_images.py`; core release/smoke code has no provider imports or adapter selection. The publishing/promotion YAML explicitly invokes that integration for the configured deployment, using existing `RAILWAY_TOKEN`/`RAILWAY_PROJECT_ID`. Ordinary PR checks/builds need no provider account. Missing deployment configuration fails the deployment step honestly.

The command resolves exactly one target environment, reads the existing pair, fails on malformed/partial state, and permits documented both-absent initial configuration. Record only the previous pair and outcome, never unrelated variables/secrets/provider payloads. Submit both keys in one collection mutation, never separate writes, then read back both. Verify the existing collection API and readback semantics during implementation using current provider evidence; do not claim stronger transactional guarantees than that operation supplies. A mismatch/error is failure, not successful deployment.

Use 10-second connection/30-second response timeouts, at most three attempts with bounded backoff, and job timeouts (60 minutes build, 10 minutes promotion). On ambiguous mutation response, read back first; matching desired pair succeeds, otherwise retry the complete pair. No automatic rollback after an unknown result. Logs/assets summarize safe errors. Locks serialize workflow writers but do not fence external operators; queued pending runs may be superseded by GitHub and need explicit redispatch.

Only rerunning the original publishing run may reuse its candidate: same stable run ID/source, validated saved pair, no rebuild once candidate exists. Before a durable candidate, partial image pushes remain ineligible/unreferenced; rerunning may build again without overwriting a recorded pair. Candidate persistence failure prevents staging. Staging failure leaves the draft for original-run retry. If finalization fails after staging, retry reuses/rechecks the candidate, reapplies/readbacks its pair and completes the final record. Existing final records are validated no-ops; do not restage an older finalized run accidentally. A draft already containing final evidence must be validated against the candidate and published without overwriting that historical evidence. Promotion reruns validate then apply/readback the selected pair, with matching current state a no-op.

## Risks, rollback and evidence

Trusted writers can modify workflows/releases; no cryptographic or protection claim closes that boundary. Out-of-band configuration writers can race workflows. Registry retention must preserve referenced digests. Desired configuration readback is historical evidence, not machine rollout or successful conversations. Reuse the existing canary/replacement/readiness process for actual adoption; in-flight replacements retain pinned targets. Rollback explicitly selects a prior compatible release through the same path, never deletes volumes. Disable defective automation before repair; do not restore the superseded direct-production rebuild path silently.
