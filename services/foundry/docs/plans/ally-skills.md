# Native Hermes skills for Allies

## Scope and outcome

Expose the broad, license-eligible Hermes catalog to every Ally through Hermes' existing `skills.external_dirs` support while keeping learned skills writable and private under each profile's persistent `skills/` directory. The initial catalog includes `xurl`, the GitHub skills, `himalaya`, and the selected defaults `grounded-citations`, `arxiv`, `humanizer`, `architecture-diagram`, `youtube-content`, `maps`, and `ocr-and-documents`. Existing and newly created profiles receive the same behavior.

This change uses Hermes' native `skills_list`, `skill_view`, `skill_manage`, official Hub CLI, and background review. It adds no catalog API, registry, product UI, or skill framework. It must not copy the four proprietary office skill packages (`docx`, `xlsx`, `pdf`, and `powerpoint`) or imply that a missing CLI credential or binary is already configured.

## Approach and affected surfaces

1. **Build an immutable catalog in the pinned Hermes image.** Add a small build-time catalog script and focused tests under `runtime/hermes-image/`. It physically copies the pinned image's bundled `/opt/hermes/skills` tree to an Allies-owned catalog directory, preserves attribution, the repository `LICENSE`, and support files, and excludes the four restricted office packages. A copy is required because Hermes resolves and validates support-file paths against trusted roots: links back to the original unfiltered directory would either fail validation or make restricted material trusted. Accept an explicit compatible skill license or the verified repository-level MIT license inherited by the nine pinned bundled skills without frontmatter license metadata; fail closed on any other unknown provenance. Install the result root-owned and non-writable by runtime UID 10000. Add one concise Allies-authored discovery skill to explain native `skills_list`/`skill_view`, `hermes skills search ... --source official --json`, prerequisite setup, and creating a uniquely named private learned skill when a shared skill needs adaptation. Update `runtime/hermes-image/Dockerfile` and the image smoke path without changing the inherited entrypoint.

2. **Verify the selected defaults against the built image.** Assert the already-present `youtube_transcript_api` dependency at image build; the other five ready defaults use only existing Hermes tools or the Python standard library. Keep the original MIT `ocr-and-documents` skill discoverable and require the Ally to check its missing local extractor prerequisites. This PR does not add PyMuPDF, marker, Tesseract, rewrite the upstream skill, or download dependencies during profile wake.

3. **Materialize the native profile contract for new and existing profiles.** In `runtime/allies_runtime/profile_store.py`, extend the generated `config.yaml` with one absolute catalog entry under `skills.external_dirs`; keep `HERMES_HOME/skills` unchanged and writable. Add pinned PyYAML to `runtime/pyproject.toml` and `runtime/uv.lock`, install it from the lock in `runtime/Dockerfile`, and add a build-time import smoke. Use a strict loader that rejects duplicate keys. Keep manifest schema v2 for rollback compatibility. During ordinary existing-profile inspection, atomically replace the exact prior Foundry-generated config and accept the exact new config. For any other existing config, enforce the existing byte bound and parse exactly one YAML document whose root is a mapping: if it has no `skills` key, append the canonical block to the original raw bytes so comments, ordering, formatting, and unrelated settings remain unchanged; if `skills.external_dirs` already semantically contains the canonical path, accept it without rewriting; otherwise return a sanitized repair result. Reject malformed YAML, multiple documents, non-mapping roots, duplicate keys, non-mapping `skills`, and ambiguous/custom `skills` blocks without overwriting them. Preserve sessions, memories, local skills, SOUL edits, credentials, and other profile state, and surface atomic write failure as repair required. Keep the catalog path a code/image default rather than a new required environment variable.

4. **Prove discovery, isolation, persistence, and learning.** Extend `runtime/tests/test_profile_store.py` for first materialization, repeat reconciliation, v2 profile upgrade, raw-byte preservation when appending beside comments and nested settings, an already-canonical skills block, malformed/multi-document/non-mapping/duplicate-key/custom-skills rejection, atomic upgrade failure, and preservation of files in the local skills directory. Extend the Hermes image CI/smoke checks to run as UID 10000 with a temporary profile: query the native `GET /v1/skills` endpoint and the underlying skill tools; expect all license-eligible Linux skills plus the Allies discovery skill; explicitly find and view `xurl`, a GitHub skill, `himalaya`, and the seven defaults; confirm local OCR extractors are absent and support files remain present; native OCR metadata does not declare these dependencies, so its `available` label is not proof of readiness and the guide requires prerequisite checks; confirm restricted office packages are absent; confirm catalog writes fail; create/read/update a uniquely named local skill with `skill_manage`; restart against the same mounted profile and confirm the learned bytes remain. Separately, drive the real foreground `run_conversation` and finalizer with a deterministic fake local provider that completes at least 10 tool iterations, supplies an explicit durable-learning signal, runs the actual background review fork, and makes that fork write a known skill through `skill_manage`; poll boundedly and assert the bytes land only in the active profile's local skills tree. This CI proof must not use an external model, network credentials, a mocked-away finalizer, or a vacuous no-op review. Production review remains asynchronous and best-effort, and may legitimately make no change when there is no durable learning signal. Do not add a new endpoint, review trigger, or lower threshold merely for production.

5. **Document the runtime truth and rollout handoff.** Update the relevant runtime/image operations note to state that bundled catalog skills are immutable shared instructions, Hub discovery is available through the existing terminal CLI, prerequisites may still report setup needed, learned skills are profile-local, and background skill review is best-effort after the native tool-iteration threshold rather than after every turn. After the PR is reviewed and merged, a separate authorized operational follow-up can publish the image and use the existing runtime-image reconciliation process for existing and new Fly workspaces. No deployment or staging configuration changes belong in this PR.

## Acceptance criteria

- A fresh profile and an exact existing v2 profile both discover the eligible bundled catalog through `skills_list`; `skill_view` loads representative catalog content.
- `xurl`, GitHub, `himalaya`, and all seven selected defaults are discoverable. Platform-incompatible entries may be omitted by Hermes' native platform filter, and missing credentials or commands remain honestly reported as setup needed.
- The four restricted office packages and any future package without an explicit compatible license or the verified pinned Hermes repository-level MIT inheritance fail the catalog build or are excluded; their bodies are never copied into the image catalog.
- UID 10000 cannot modify the shared catalog. `skill_manage` creates and updates a uniquely named skill only under the active profile's local `skills/`; a second profile cannot read or mutate it.
- Reconciliation and container restart preserve existing sessions, memories, SOUL changes, credentials, and locally learned skills byte-for-byte; custom config bytes also remain unchanged except for the appended canonical block when no `skills` key exists.
- The normal `run_conversation` finalizer path, after at least 10 tool iterations, performs a bounded background skill review and the deterministic test's resulting mutation is profile-local. Runtime review remains best-effort and may be a no-op when there is no durable learning signal.
- PyYAML is locked and installed in the runtime image, the existing YouTube dependency is verified in the Hermes image, and profile wake performs no package or skill downloads. OCR remains honestly setup needed.

- `make hermes-image-test`

- `make check` and `make validate` before review, followed by separate simplicity and correctness reviews required by repository policy.

## Risks, rollback, and open decisions

- A catalog name can collide with a learned local skill. Hermes intentionally searches the profile-local directory first and rejects ambiguous creation; the discovery skill must require a distinct private name rather than promising an overlay with the same name.
- Build-time license classification can drift when the pinned Hermes base changes. Keep the source SHA/digest pin, preserve the repository `LICENSE`, recognize only the inspected nine-skill repository MIT fallback, and fail closed on other unknown licensing; re-run the inventory when that pin changes.
- Background review is asynchronous and best-effort, so its integration test needs a bounded poll, a deterministic fake local provider, and an explicit learning signal. The test asserts a write for that controlled review while the production contract does not promise a write for every turn.
- Rollback is an image rollback through the existing immutable image reference. Existing profile-local learned skills remain on the volume; a profile upgraded to the new config may retain an unavailable external directory under the old image, which Hermes already skips, and a later reconciliation can remove it through another versioned managed-config upgrade.

No product decision remains open. Local OCR enablement is explicitly deferred.
