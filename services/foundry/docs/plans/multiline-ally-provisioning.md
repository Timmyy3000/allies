# Multiline Ally provisioning

Status: revision 2, accepted ADV-001 through ADV-004 and SIM-001 incorporated; ready for implementation handoff. Route: fast. HTML required: no. Scope: Cloud and Foundry; PRs target `dev`. No merge, deployment, or existing-record recovery is authorized.

## Outcome and contract

Normal LF line breaks in user-authored job and personality must survive onboarding, creation, provisioning, rendered SOUL content, and materialization. Keep job at 200 characters and personality at 4000 characters, retain existing job outer trimming and personality whitespace preservation, and leave name, identifier, tenant, credential, and lifecycle rules intact.

Use one small Cloud field helper, shared by public-schema before validators and `normalize_seed`. Replace CRLF pairs with LF in job/personality before Pydantic's 200/4000-character limits, service validation, persistence, content comparison, and fingerprint calculation. Before replacement, require a string and cap raw field length at twice its canonical limit (400/8000 characters); CRLF contraction cannot make a longer raw value valid. Preserve the deployment/Django request-body bound and test that oversized bodies are rejected; do not remove or enlarge body limits to enable this fix. Then enforce the canonical 200/4000 limits before existing job trimming. Reject remaining bare CR; do not flatten lines, collapse blank lines, normalize Unicode, or trim personality. The internal v1 provisioning request carries canonical LF only and rejects CRLF/bare CR rather than silently changing fingerprint-bound content.

For job/personality, reject Unicode categories `Cc`, `Cf`, `Zl`, and `Zp` except LF. This retains Foundry's current unsafe-control protection, including TAB, NUL, DEL, C1 controls, format controls and Unicode line/paragraph separators. Apply this at Cloud normalization and its gateway model, and adjust Foundry's regex and Unicode validator together to permit LF only for those two fields. Keep Foundry's name validator unchanged; do not reuse a multiline validator for identifiers or other strings.

Cloud's request fingerprint remains its opaque accepted-content identity. Foundry echoes it and independently computes its seed digest over rendered content; these two digests are not equal by design. Keep all hashing algorithms, deterministic binding-to-profile identity and materialization receipts unchanged. Add only the narrowly bounded legacy replay comparison below. No schema migration, data rewrite, new dependency, or runtime image change is expected.

## Compatibility, risks and rollback

Existing accepted LF/single-line content keeps identical normalized values and hashes. Preserve pre-change CRLF operation replay without rewriting its Ally, onboarding attempt, operation fingerprint, status or timestamps, and without enqueueing dispatch. The existing workspace/user/idempotency-key lookup and consumed-attempt token/browser checks remain mandatory.

On ordinary fingerprint mismatch only, allow a compatibility comparison when the matched operation's retained Ally job/personality actually contains CRLF. Canonicalize those retained two fields in memory with the same helper and require equality with submitted canonical job/personality; unsafe legacy text is not eligible. Construct legacy hash candidates from the submitted values with only job/personality replaced by their retained original byte-for-byte text. Calculate the two already-supported hash projections (with and without onboarding-attempt digest); require the stored operation fingerprint to match one. Every other submitted field, including reply, name and appearance, participates unchanged. Never accept solely on normalized field equality or use retained values to replace unrelated submitted fields. Return the existing result through the existing attempt/binding authorization path. A corrupted fingerprint or meaningful content change still conflicts.

For an unconsumed pre-change CRLF onboarding attempt, compare its text fields canonically in memory against the new submission; preserve all other comparisons and existing attempt authorization. A new accepted Ally uses canonical LF. Do not rewrite the retained attempt's text as a migration or introduce a recovery action. Existing completed/failed operations replay their existing status, never resume work. The existing reported records remain untouched.

Regression fixtures must represent pre-change hashing directly, not create them through the new normalizer. Cover CRLF and LF replay of old operations under both existing hash projections, mixed LF/CRLF fields, unchanged rows and no enqueue, altered text/reply/name/appearance, wrong token/browser/user/workspace, and corrupted stored fingerprint. Include a valid unconsumed legacy attempt and verify no stored text rewrite. This compatibility path applies only to the matched retained CRLF operation; it is not a global fallback or a new fingerprint version.

The principal risk is normalization after hashing or different normalization at onboarding and creation. Centralizing it before durable acceptance and proving replay prevents that. A second risk is relaxing both regex and category checks too broadly; the explicit LF-only exception and negative matrix constrain it. Generic seed validators remain compatible with existing persisted profiles, while the external authoring boundary retains its stronger control policy.

Rollback runs in reverse dependency order: the delivery owner must revert Cloud or operationally disable affected new creation before reverting Foundry. Because old Cloud already accepts LF, a Cloud revert alone is insufficient to protect new LF requests: suspend new multiline provisioning (or all new creation through existing operational controls if no narrow control exists) before Foundry rollback, and account for in-flight new operations without resetting/requeueing customer records. Verify that acceptance is stopped before removing Foundry LF support. No data rollback, new feature flag or recovery command is part of this fix; preserve already accepted data and existing fingerprints.
