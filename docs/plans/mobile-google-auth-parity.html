Allies mobile · implementation plan

Mobile Google sign-in parity

Make mobile account access match the existing web Google-only passwordless flow, while reconnecting the existing native PKCE and session boundaries.

Feature overview

  • Replace the mobile placeholder with one centered orange Google action.
  • Reuse the existing typed Cloud client, native PKCE flow, callback validation, and secure session adapter.
  • Preserve safe return paths and unrelated onboarding work.

Scope

In scope

  • Google-only mobile sign-in, matching apps/web/app/sign-in/sign-in-client.tsx and its stylesheet for copy, states, and design.
  • Native browser/app-link return handling and the protected-route guard.
  • Focused tests for callback validation, flow state, errors, and routing.
  • Real auth initialization when configured, independent of local mock product data.
  • Session guarding is enabled when the Cloud client exists; a client-less build keeps the mock walkthrough.

Out of scope

  • Username/password fields, account creation, new dependencies, Cloud changes, web changes, and unrelated routes.

Contracts and state

createGoogleSignInFlow owns one in-memory PKCE attempt, opens the browser, accepts one validated callback, exchanges the code, and returns a bounded GoogleSignInOutcome. useGoogleSignIn owns transient UI state. NativeSessionProvider and its adapter own the durable session and account.

SurfaceState/behavior
Google buttonContinue with Google → Opening Google…; disabled during the flow.
Live statusOpening a secure Google sign-in… while the browser is opening or waiting.
CallbackAccept only the configured redirect URI, matching state, and a code; reject stale or malformed input.
RoutingSigned-out protected routes go to sign-in; signed-in auth entry routes go to a validated /allies, /allies/new, or one-segment /allies/<allyId> target, otherwise /allies.

The existing native Cloud endpoints remain the transport boundary: the Google start request sends redirect_uri, code_challenge, code_challenge_method: "S256", and state; the token exchange at POST /api/v1/auths/native/token sends grant_type: "authorization_code", code, code_verifier, and redirect_uri. No duplicate client or backend rule is added.

Implementation phases

Phase 1: Reconnect native auth

  • Restore only the PKCE, callback listener, Google flow hook, auth-return route, and session-route guard required by the flow.
  • Reconcile imports with the current providers, preserve mock onboarding behavior, and remove only the provider guard that prevents configured auth from initializing.

Phase 2: Match web and verify

  • Replace the placeholder with the single web-equivalent Google pill.
  • Map cancellation, unavailable, invalid-return, and generic failures to clear retryable messages.
  • Run focused auth tests, mobile lint/typecheck, regression tests, and git diff --check.

Acceptance criteria

  1. No username, password, or create-account UI appears on mobile sign-in.
  2. The button, loading copy, live status, and error behavior match web.
  3. Only a valid PKCE callback can complete sign-in; duplicate or stale callbacks are safe.
  4. Successful sign-in persists through the existing session provider and reaches a safe destination.
  5. Signed-out protection and mock onboarding behavior remain correct.
  6. Configured authentication can initialize while mock product content remains available.
  7. Return targets are limited to /allies, /allies/new, or one-segment /allies/<allyId>; deleted nested routes are rejected.
  8. A client-less build keeps the mock walkthrough; a configured client enables session guarding and real Google access.
  9. Unrelated dirty files are not restored or overwritten.

Test plan

  • Test valid, malformed, wrong-origin, wrong-state, canceled, duplicate, transient, and generic flow outcomes.
  • Test route actions for checking, signed-out, offline, signed-in, and unsafe return targets.
  • Manually verify the sign-in screen, cancel/retry behavior, successful return, and protected-route redirect in a configured native build.
  • Before device proof, verify the Cloud redirect allowlist, hosted platform-link association, and a fresh binary with generated link entitlements.

Risks and mitigations

  • Missing native redirect registration: disable the action with a configuration message instead of fabricating a URI.
  • Malicious or duplicate callbacks: validate URI/state/code, allow one active flow, and dispose the listener.
  • Dirty parallel work: patch focused paths in place and inspect the final status/diff.
  • Stuck loading state: reset transient flow state in finally and allow retry.
