Allies Cloud · implementation plan · CLD-009

Native onboarding without weakening web

Make the existing onboarding attempt and authenticated Ally creation sequence work for Android and iOS, while preserving browser Origin and CSRF protection, server-authoritative abuse controls, honest errors, and one-time attempt semantics.

Planning statusRevised · simplicity review passed · fast-path self-approved

Adversarial findings are resolved in the closed native-session boundary, keyed attempt fingerprint, distinct throttle mapping, PostgreSQL race coverage, and separate approval/merge/deployment gates.

Feature overview and primary decision

Problem. POST /api/v1/onboarding/attempts always applies the browser Origin and CSRF contract. A valid mobile request has no browser cookies, Origin, Referer, or CSRF header, so staging rejects it before greeting generation.

Target users. New Allies users on Android and iOS, plus existing web users whose onboarding security must remain unchanged.

Success. The current mobile client receives the official attempt token and greeting from staging, carries that attempt through native Google sign-in, and creates the Ally without inventing a client-trusted identity.

Decision: keep the existing versioned route and request body. Select one of two closed transport branches. Any browser or session signal selects or rejects the browser path. Only a signal-free public attempt may use native, and only behind the existing native feature gate and server-authoritative throttle.
Incoming attempt→Any Origin, Referer, Cookie, CSRF, or Authorization?→Yes: browser checks, never fallback·No: native gate + identity + throttle→Existing generation service

Native create predicate. The bearer bypass is selected only for a syntactically valid bearer with no Origin, Referer, access/CSRF cookie, X-CSRFToken, or other browser/session signal, and only after the resolver validates SessionClientKind.NATIVE. Browser-kind bearers, invalid bearers, and every hybrid combination stay on the browser/error path and cannot bypass CSRF.

The native requester prefix is an abuse-control identity only, not ownership. Native ownership is possession of the high-entropy short-lived attempt token, exact seed equality, one-time consumption, and the authenticated user's Workspace capability. Browser attempts keep the CSRF-cookie binding.

User stories

  1. Mobile preview works without browser state and displays the Cloud greeting.
  2. Invalid, throttled, disabled, or unavailable requests return truthful recoverable errors without private details.
  3. Web onboarding retains trusted-origin and CSRF protection.
  4. The pre-sign-in attempt remains valid for one authenticated native create without IP ownership.
  5. Deployment owners have one reversible gate and schema/device evidence before closure.

Scope

Route

Existing attempt and create routes only.

Gate

ALLIES_AUTH_NATIVE_ENABLED, default false.

Migration

None. Reuse the binding digest field.

In scope

  • Add a strict native branch to the existing attempt route while preserving browser behavior.
  • Reuse the existing native gate, which production-validates Railway mode, shared cache, and native Google configuration.
  • Add the onboarding native throttle operation at 5 requests per normalized prefix per 60 seconds, sharing the existing native global ceiling. Existing provider generation budget and global concurrency remain a second cost-specific layer.
  • HMAC the normalized prefix before generation admission. Never log or persist the raw address or prefix.
  • Store HMAC("native:" + attempt_token) in the existing binding digest for native attempts; retain HMAC(CSRF cookie) for browser attempts.
  • Allow authenticated native bearer create after the existing session-kind resolver and Workspace capability check.
  • Preserve exact seed, TTL, one-time consume, idempotency, provider validation, generation admission, and safe envelopes.
  • Publish both transports, security, no-store, and stable errors in OpenAPI; add focused tests and Railway runbook evidence.
  • Require staging schema, edge, Android, and iOS evidence before ticket closure.

Out of scope

  • Interface runtime or UI changes; the current client already sends the accepted body without credentials.
  • New route, request field, client identity, attestation, app secret, installation registry, dependency, table, or migration.
  • AUTH-002 token, PKCE, Google provider, redirect, SecureStore, or session-family changes.
  • Chat and other native mutations, prompt/content changes, live config, deployment, EAS publication, device install, commits, pushes, or PRs in this planning run.

Dependencies and assumptions

  • Railway is the only public staging ingress and overwrites X-Real-IP; the owner must confirm the accepted anti-spoof proof before enablement.
  • Redis remains the shared Django cache for native throttles and generation admission.
  • The one gate covers onboarding and native Google continuation because the flow needs both.
  • The attempt token retains at least 256 bits of entropy, keyed-digest storage, 1,800-second expiry, and no logging.
  • The live staging OpenAPI fetched 2026-09-04 was HTTP 200, SHA-256 30c3552e5468abf88372d8cb243cb3d6c178b26c7495118befc6e0a060663856, with the routes present but no onboarding transport/header detail and generic errors.
  • Android 1.0.3 preview was queued; iOS has no preview until Apple internal-distribution credentials exist.

Phases

01

Transport and ownership boundary

Goal: current public attempt and authenticated create work natively without weakening web.

  • Classify strict browser/session signals; preserve browser checks.
  • Gate native, run check_native_rate_limit(request, "onboarding") before provider/database, map identity/cache failure to 503 and exhaustion to 429.
  • HMAC the prefix for generation admission; bind native attempts to token capability.
  • Use an explicit no-browser-signal native-create predicate, then the existing SessionClientKind.NATIVE resolver and Workspace checks; do not use the unsafe generic Origin bypass for hybrids.
  • Reject hybrid/cross-transport; never fallback from failed browser checks.

Exit: focused tests prove native continuation, browser compatibility, cross-transport rejection, stable errors, idempotency, and no sensitive persistence.

02

Publish and verify the contract

Goal: generated OpenAPI describes implemented behavior.

  • Add transport matrix, public security, browser header guidance, no-store, safe examples, and authenticated create alternatives.
  • Add setting/deployment inventory and Railway enablement plus rollback guidance.
  • Run focused and full validation, CI, Gitleaks, and Enkii general/code/security/policy; resolve P0-P2 or record an authorized exception.

Exit: schema tests pass, no route/body/dependency/migration drift, and review lanes clear or an exact external blocker is recorded.

03

Promote, synchronize, and prove devices

Goal: align source, staging schema, edge behavior, and installed apps.

  1. After separate merge authorization, merge to dev, promote exact revision to staging, confirm Railway web/worker/beat SHA.
  2. Confirm anti-spoof and shared-cache proof before enabling native.
  3. Fetch staging OpenAPI, record SHA-256, assert reviewed onboarding fields.
  4. Only if schema bytes changed, make a separate Interface-owned snapshot/metadata refresh and run bun run cloud:generate plus bun run cloud:check; no runtime client change unless a real delta proves it.
  5. Run Android real-build proof, then iOS after signing credentials. Expo Go is not evidence.
  6. Capture sanitized 200, token/greeting keys, preview, reply, system-browser Google, create, and web regression evidence. Redact all secrets.

Exit: both platforms pass, browser passes, schema and deployment agree, evidence names Cloud and Interface revisions. Missing iOS credentials leaves CLD-009 externally blocked.

Acceptance criteria

  1. Signal-free native staging attempt returns 200 token/greeting and Cache-Control: no-store.
  2. Browser/hybrid never falls through. Trusted browser with CSRF succeeds; existing 403 codes remain.
  3. Native uses only accepted Railway identity, requester limit, shared native ceiling, and generation controls. Identity/cache failure does no provider/database work and returns 503.
  4. Requester/generation exhaustion is 429 throttled; provider/admission unavailable is 503 onboarding_unavailable; invalid input is 422 validation_error.
  5. Native attempt survives Google continuation and is consumed once by native bearer with Workspace write, exact seed, stable idempotency key.
  6. Cross-consumption, tampering, expiry, replay, foreign Workspace, and changed-content idempotency fail without attempt-existence disclosure.
  7. No raw token, CSRF, address, prefix, Authorization, or provider detail in logs, DB, schema examples, or evidence.
  8. OpenAPI covers unchanged body, both branches, no-store, create auth alternatives, and every stable error.
  9. No dependency, route, table, migration, client field, or Interface runtime change.
  10. Focused tests, make check, make lint, format, full tests, coverage, PostgreSQL, Gitleaks, and all Enkii lanes pass.
  11. Staging schema/behavior match promoted SHA and Android plus iOS real-build proof exists. Deployment/signing blockers keep acceptance open.

Backend and frontend considerations

Queries, N+1, and migration

  • Attempt remains one insert after provider success. Native identity/throttle are cache operations and add no query.
  • Create retains indexed token-digest select_for_update, Workspace capability, and idempotency lookups.
  • Expected change is zero browser queries and zero DB work before native admission. Assert no row for rejected/throttled/unavailable requests.
  • No N+1 applies because no relation collection is iterated.
  • No migration. makemigrations --check --dry-run must stay clean; any model field/enum need returns to planning.

Detailed unit cases

  • Happy: browser attempt; valid native attempt; native attempt then bearer create; exact create replay.
  • Validation: empty/overlong/extra seed, malformed/comma IP, browser marker without security, bearer on public attempt.
  • Security: forwarded/client IDs ignored, secrets absent from logs/storage, cross-transport fails, foreign Workspace non-disclosing.
  • Abuse: onboarding and global ceilings, generation budget/concurrency, cache unavailable, no provider/row after pre-admission failure.
  • Failures: provider unavailable/unknown/invalid, admission unavailable, requester/generation throttle, disabled gate, expired/consumed token.
  • Compatibility: browser Origin/CSRF, session-kind, seed/idempotency, schema examples, no-store.

Frontend data and state

User enters preview; existing beginOnboarding omits credentials; backend selects native, admits, generates, validates, stores, returns token/greeting; UI retains token and greeting; reply is retained; native Google returns bearer; create sends same token, seed, reply, and idempotency key. A 422 is correctable, 429 means backoff, 503 means unavailable/retry, and a mobile 403 means unexpected hybrid/browser signals, not a generic network error.

No state change: existing mobile onboarding state and encrypted pending command remain authoritative. Cloud must not require browser state or device identity.

Mobile sequence

  1. Land and validate Cloud first.
  2. Promote exact revision and verify live OpenAPI before Interface snapshot refresh.
  3. Regenerate existing Interface artifacts only; do not hand-edit generated types or alter runtime without a proven delta.
  4. Run Android real-build proof when 1.0.3 is available.
  5. Provision Apple signing, build iOS preview, and repeat proof before closure.

Rollback procedure

  1. Through authorized Railway configuration, set ALLIES_AUTH_NATIVE_ENABLED=false and redeploy the exact staging revision. New native attempts/create stop; browser stays unchanged.
  2. Verify browser attempt/create and live schema. Schema description must state the gate even while disabled.
  3. Do not delete existing attempts. They contain no account ownership and expire through existing TTL/cleanup.
  4. If config rollback is insufficient, revert the focused Cloud commit and promote normally. There is no database rollback.

External decisions and proof still required

  • Deployment/security owner confirms Railway overwrites forged X-Real-IP, has no alternate public ingress, and both web workers share Redis. Keep native disabled without this.
  • Plan approval, PR approval, merge authorization, staging promotion, and feature-flag change are separate owner decisions; this task does not infer any of them and leaves the PR unmerged.
  • Interface-owned schema refresh after live publication; reconcile, do not hide, the pre-existing snapshot metadata mismatch.
  • Apple signing credentials and an iOS preview. Android cannot waive the accepted iOS requirement.
