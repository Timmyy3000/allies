# Real approval flow extension

## Scope and verified baseline

Deliver this as a separate approval slice after the independent meaningful-activity PRs. It replaces the current attention-only `awaiting_action` experience with one-operation Approve/Reject control; it does not broaden an approval to a session or permanent allowlist. Unless the user selects generalized business-action approvals, the first slice covers Hermes' existing blocking dangerous-terminal and `execute_code` gates. Unsupported approval categories return a normal denied result immediately, perform no action, and let the Ally explain instead of leaving the run waiting.

- Hermes already has the enforcement primitive: `tools/approval.py` queues a dangerous operation, blocks its agent thread for up to the configured timeout (300 seconds by default), and returns a normal denied/timeout result so the agent can continue and explain. Interrupts fail closed. `/v1/runs` registers a run-scoped notifier, emits `approval.request`, and accepts an authenticated `POST /v1/runs/{run_id}/approval` decision.
- Foundry does not use that run API. `allies_runtime` calls the persisted-session `POST /p/{profile}/api/sessions/{session}/chat/stream`. That route creates a `run_id` but registers no approval notifier or resolver state; its SSE disconnect cancels the turn. The runtime parser rejects approval events and applies a fixed 15-second stream deadline.
- Foundry accepts `execution.awaiting_action`, but its exact payload is only `{action_kind}`. It creates an ordered event under the active lease; there is no pending-approval model, execution state, Cloud decision endpoint, or runtime decision-poll contract. The worker renews the lease while the stream remains open. A lost/fenced lease fails a checkpointed execution rather than safely replaying it.
- Cloud projects the event as generic `Action required` / `awaiting_action`. It has no Approval record, mutation endpoint, or durable delivery path back to Foundry. Cloud already owns membership checks, CSRF/native bearer policy, ordered Foundry receipts, and idempotent service-to-service dispatch patterns.
- Interface already contains a fixture-only `ApprovalSheet`; production tests require Approve/Reject to be absent today. Aphrodite `allies-current`, file `gdQOp0ScM7kR6XB7ooK5Du`, node `355:6222` confirms a dimmed mobile overlay and bottom sheet with close, an action question, Reject, and Approve. The design does not define identity, expiry, network, or close semantics. Close is therefore a local dismiss and leaves the approval pending.
- Existing Hermes guards cover dangerous terminal/`execute_code`, plugin approval gates, and MCP elicitation. They are not evidence that every product action such as send, publish, spend, share, or delete is currently intercepted. The first release uses an explicit supported action-kind allowlist; generalized business actions need their own enforcement hooks and a later contract review.

## Contract and ownership

Cloud owns the user-visible Approval and the durable first decision. Foundry owns the current execution/attempt binding and a durable mirror used to deliver that decision. Hermes owns enforcement and the live blocked tool call. Interface talks only to Cloud.

```text
Hermes blocked tool -> session SSE approval.request
  -> runtime appends execution.awaiting_action under its current lease
  -> Foundry persists pending request and delivers its bounded approval contract
  -> Cloud creates Approval -> Interface opens sheet
  -> Cloud records decision first, then claims/retries that Approval row
  -> Foundry validates current attempt/generation and exposes decision to that lease holder
  -> runtime resolves the exact Hermes request -> the same agent turn continues
```

Use three identities rather than exposing runtime internals:

- `hermes_approval_id`: opaque, unique within one Hermes `run_id`; remains inside the runtime boundary.
- `approval_request_id`: Foundry UUID bound to workspace, profile, execution, attempt, generation, Hermes run, Hermes approval, and expiry; service-to-service only.
- `approval_id`: Cloud UUID exposed to Interface. Public responses must not contain Foundry execution/attempt/lease IDs, Hermes run/request IDs, arbitrary tool results, or secrets. Material action details live only in the membership-authorized approval-detail response, never in the generic activity snapshot/SSE.

Hermes session SSE adds `approval.request` with exact `session_id`, `run_id`, `hermes_approval_id`, allowlisted `action_kind`, guard-owned `action_label` (1–120 Unicode characters), complete `action_preview` (1–16 KiB UTF-8, no NUL), and aware `expires_at`; it also emits `approval.responded` for `approved`, `rejected`, `expired`, or `cancelled`. For terminal/code gates, the preview is the exact proposed command or script after forced secret redaction, because a generic category is not informed consent; file paths, destinations, recipients, URLs, and other material targets remain when needed to understand the action. Never copy model-written descriptions or arbitrary tool output into the preview, silently truncate it, or claim every action is safely summarizable. If the guard cannot produce a complete meaningful preview inside the bound, it fails closed without presenting an approval. Add an Allies session resolver bound to the original profile Bearer credential, `X-Hermes-Session-Key`, profile, session ID, run ID, and exact Hermes approval ID; all tuple members must match the live request before it may apply `once` or `deny`. The private decision body also carries aware `deadline_at = min(expires_at, acknowledgement_deadline_at)`, which Hermes checks before signalling the waiter so delayed HTTP delivery cannot outlive consent. Preserve the existing `/v1/runs` FIFO/no-ID resolver solely for legacy clients. Exact repeats are idempotent; another choice or a post-terminal decision conflicts and cannot resolve a different queued request.

Foundry accepts two mutually exclusive `execution.awaiting_action` schemas unconditionally: legacy exact `{action_kind}` remains attention-only; rich exact `{approval_request_id, action_kind, action_label, action_preview, expires_at}` is actionable, with UUID request ID, the existing safe-code `action_kind`, the preview bounds above, and an aware future expiry inside the configured cap. Its pending record has `pending|decision_recorded|applied|expired|cancelled|outcome_unknown`, timestamps, immutable `approve|reject` decision/fingerprint, and attempt/generation bindings. A Cloud-authenticated, canonical-fingerprint decision command carries the exact request correlation, `decision: approve|reject`, one UUID idempotency key, issue/deadline timestamps, a fixed `acknowledgement_deadline_at = decided_at + 30 seconds`, and Cloud/Foundry scope. Under a transaction, the first valid choice wins; an exact replay returns the stored receipt and a conflicting choice returns 409. Expired, stopped, terminal, lost-lease, or fenced attempts cannot be resumed. A runtime-authenticated `execution.approval_resolved` event with exact `{approval_request_id, outcome}` records only `approved|rejected|expired|cancelled`, consumes the next ordinary attempt sequence, and is the authoritative acknowledgement that Cloud may use to leave `decision_recorded`.

The runtime publishes the pending event, then waits on a bounded Foundry decision poll while its existing lease renewer stays active. Only the named approval wait may replace the 15-second Hermes read deadline, and only until `expires_at`; ordinary stream timeouts remain unchanged. After consent expires, the parser allows one ordinary read-timeout interval solely to receive the exact expiry acknowledgement and subsequent explanation; this grace never permits a decision or execution. It submits the exact request and decision to Hermes and then resumes reading the same SSE turn. An ambiguous Hermes acknowledgement permits only status/receipt reconciliation for at most 30 seconds from `decided_at`; it never resends or delivers a late decision, extends consent, executes after the acknowledgement deadline, or creates/replays the execution on another attempt. If no matching runtime acknowledgement exists at that deadline, Foundry treats the request as cancelled and Cloud exposes terminal `outcome_unknown` with honest copy.

Cloud creates one Approval transactionally with the accepted rich event and preserves the existing receipt sequence. Store workspace, Ally, conversation, message, public approval ID, private request correlation and preview, action kind/label, `pending|decision_recorded|approved|rejected|expired|cancelled|outcome_unknown` status, request/expiry/decision/acknowledgement-deadline timestamps, deciding user, decision idempotency/fingerprint, and delivery claim state on this same row. Reuse the existing bounded claim/fence/retry pattern; do not add a second decision-outbox model or expiry scheduler. `GET /api/v1/workspaces/{workspace_id}/conversations/{conversation_id}/approvals/{approval_id}` requires membership plus `Capability.PROFILE_READ` and returns the label/full redacted preview. `POST .../approvals/{approval_id}/decision` requires membership plus `Capability.PROFILE_WRITE`, accepts exactly `{decision: "approve"|"reject"}` plus `Idempotency-Key`, applies existing origin/CSRF or native-bearer checks, records `decision_recorded` before one timely delivery, and makes that Approval row claimable only inside the original consent window. An exact retry returns the same result; different content under the key, a second choice, expiry, read-only/foreign access, or a stale scope returns a bounded conflict or authorization error without delivery. Generic activity snapshot/SSE exposes only nested `approval: {id, status, expires_at, decided_at?}` on the corresponding awaiting-action entry; the client maps it to camel case and fetches detail separately. Cloud moves to approved/rejected only from the matching `execution.approval_resolved` event, so the UI never claims runtime continuation from the service delivery receipt alone.

Expiry is effective at the exact stored timestamp without waiting for a job: every Cloud/Foundry approval read, decision attempt, delivery claim, runtime poll, and client timer lazily reconciles `pending` to `expired` once `now >= expires_at`. `decision_recorded` receives only the 30-second acknowledgement reconciliation above; at its deadline, reads/claims/polls/client state reconcile it to terminal `outcome_unknown`, stop delivery, and cancel any still-pending runtime request. Neither deadline can extend consent or authorize a late execution.

The first release inherits Hermes' five-minute approval timeout. The oldest pending approval opens first and every dismissed pending item has a reopen affordance; exact IDs still determine the decision. After a click, the sheet says **Decision recorded** and the activity says **Waiting for Ally** until the matching runtime acknowledgement arrives. At acknowledgement timeout, use honest terminal copy such as **Decision recorded; Ally outcome could not be confirmed** and offer no retry that could execute the action.

## Risks and concrete open decisions

- **Action coverage:** the assumed first slice is existing dangerous terminal/`execute_code`; generalized send/publish/spend/share/delete approval needs concrete enforcement hooks and guard-owned previews before it can become actionable.
- **Acknowledgement loss:** the fixed 30-second window may end as `outcome_unknown` even if the action completed but its receipt was lost. Honest status is safer than resending consent or claiming success.
- **Preview suitability:** exact redacted command/code is sometimes technical, but omitting its material targets is unsafe. Visual/product review must confirm the scrollable detail treatment without weakening the fail-closed completeness rule.
- **Process loss:** Hermes’ wait queue is in memory. The minimum safe release keeps the same live process/attempt and treats process loss, lease loss, or fencing as expired/cancelled/failed. Durable replay of a partially executed tool call is out of scope until Hermes has a resumable checkpoint protocol.
