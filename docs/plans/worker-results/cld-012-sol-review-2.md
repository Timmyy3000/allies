# CLD-012 independent plan review — revision 2

## Verdict

Needs revision before Luna implementation.

## Actionable findings

| ID | Severity | Area | Exact evidence | Impact | Confidence | Required plan change |
| --- | --- | --- | --- | --- | --- | --- |
| SOL2-001 | P1 | Resume versus due-admission race | `docs/plans/cld-012-routines-contract.md:148-167` defines create, update/reschedule, pause, delete, duplicate-admission, active-run, and approval-replacement races, but it omits resume racing a stale scheduler candidate. The accepted Nabu specification requires resume to use the next scheduled time without replaying intentionally paused occurrences. The proposed dedupe key at line 167 does not prevent a pre-resume candidate for a paused interval from being admitted after resume unless that candidate's schedule generation/revision is fenced. | CLD-013 could incorrectly execute an occurrence that became due while paused, violating the no-catch-up requirement, or disagree about whether a concurrent resume makes a stale candidate eligible. | High | Add resume-before/after-due-admission rows. Require every due candidate to carry the routine revision or schedule generation observed when selected and reject it after any pause/resume transition unless it still represents the newly computed next future instant. Freeze expected codes, outbox counts, snapshot revision, and PostgreSQL enforcement vectors for both lock winners. |
| SOL2-002 | P1 | Crash after approval authorization CAS | `docs/plans/cld-012-routines-contract.md:131-146` correctly makes Foundry's database clock, generation fence, permission consumption, and transition to `authorizing`/`working` atomic, but line 133 only says an unknown action outcome is reconciled without replay and line 146 merely lists “action crash after CAS” as a future vector. It does not freeze a durable post-CAS action identity/state or the outcome when the process dies before, during, or after the external side effect. | A restart cannot safely distinguish “authorized but not started,” “side effect may have happened,” and “completed but receipt lost.” Implementers may either silently replay an already-performed action or strand an authorized run indefinitely, contrary to the accepted no-silent-replay and truthful-failure rules. | High | Extend the contract with durable action-attempt identity and monotonic states around side-effect dispatch. Define which transitions may be retried, how an ambiguous external outcome becomes a truthful terminal/manual-reconciliation result, and how stored receipts resolve duplicates. Give the action-crash vector explicit expected postconditions for crash before dispatch, unknown response after dispatch, and completion-receipt loss; do not permit whole-prompt or non-idempotent action replay. |
| SOL2-003 | P2 | Reproducible Class B service launch | `docs/plans/cld-012-routines-contract.md:350-359` accurately separates offline diagnostics from the real inherited `/init` service/worker probe and gives the in-container probe command, but the service launch is still prose: line 357 says to “launch the resolved image” and that an existing bootstrap must populate the socket/profile files without naming the existing bootstrap command, required mounts/environment references, or readiness-to-probe sequence. The ticket requires reproducible feasibility evidence. | Luna can implement a machine-specific launch that another reviewer cannot reproduce, and a setup failure may be misclassified because the boundary between harness setup and Hermes capability is not executable. | Medium-high | Name the existing repository bootstrap/provisioning command or script that Luna must reuse and provide the complete secret-safe container-launch template using only opaque credential references and disposable paths. If no current command can launch inherited `/init` with the required socket/profile materialization, state that as a setup blocker and make creating one bounded harness launcher an explicit impacted file. Keep the current rule that missing setup is not a Hermes capability failure. |

## Disposition recommendation

Revise and re-review. SOL-001, SOL-004, and SOL-005 are adequately corrected; the offline-versus-real-probe acceptance split is honest, but its reproducible launch remains incomplete. Do not start Luna until SOL2-001 and SOL2-002 are resolved; resolve SOL2-003 in the plan so the required Class B evidence is portable rather than workstation-specific.
