## Implementation steps and acceptance

1. **Repair Activity layout and reachability (AT-034, AT-040).** Reproduce on the production Home frame with a long active disclosure and a historical disclosure at the canvas bottom. Keep the actor in its reserved column and let content wrap/shrink without crossing it; start with CSS and the existing observer path, changing measurement only if reproduction proves it stale. On user expansion bring the disclosure into the conversation canvas's visible area using native scrolling. For content taller than the available viewport, retain an accessible scroll path to every entry; do not promise simultaneous visibility or create a floating dropdown engine. Preserve summary keyboard operation/focus, reduced motion, header/composer clearance, and manual history reading (no repeated forced jump on every stream update). Check collapsed/expanded, narrow/desktop, docking and resize.

2. **Place approvals and refine the existing sheet (AT-035 and approval placement).** Keep a single conversation-scoped query/selection/intent owner; expose its list presentation at message slots through the smallest existing component composition change, rather than mounting a polling controller per message. Match `approval.messageId` to its triggering user message and render after that message's activity entries, including active activity in the presence row. Retain previous approvals and reopening. An approval whose message is not loaded must remain reachable in an explicitly unassociated fallback, never attached to the newest turn by guess; it moves to its proper slot when history loads. The public summary has no turn ordinal: do not infer a retry ordinal. Keep one dialog, native modal focus behavior and focus return. Scope desktop centering/greater bounded width to the approval sheet; keep the mobile bottom sheet and style every actual approval scrolling container with the existing product scrollbar rules. Long previews and 200% zoom must fit without inaccessible actions or horizontal page overflow.

   Insertion invariant: each approval ID has exactly one list location. If its message owns the currently displayed presence activity, insert its list immediately after that activity inside the presence content column. Otherwise, if its user message is visible, insert after the last activity group for that message in the message row (or after its turn content if there are no entries). Otherwise insert in the unassociated fallback after the transcript. When active activity becomes historical, move the list with it to the message row; when missing history loads, move it out of the fallback. These moves must preserve selected approval and decision intent, never duplicate the list or mount another query owner. Test active → completed → next active message plus missing → loaded history with two distinct approval IDs.

3. **Close on durable decision truth (approval durability).** Gate decision-triggered automatic dismissal on a matching approval's authoritative `decision_recorded` or confirmed `approved`/`rejected` result, from submit or later polling after an uncertain response. Keep pending, transport failure, expired and cancelled states honest; none independently proves the user's choice recorded. Preserve same-choice retry keys, duplicate prevention, stale-response precedence and read-only restrictions. Prevent stale pending polling from immediately reopening an automatically closed sheet; retain a reopen control and truthful waiting/outcome status. Preserve explicit Close/Escape as dismissal without deciding, including uncertain requests; the durable-state condition governs automatic completion, not trapping the user. If deployment responses lack the typed recorded state, leave automatic completion pending and record a concrete dependency for approval-contract work. Do not fake a successful acknowledgement.

   Minimal monotonic evidence rule: retain the latest strongest validated public evidence per approval ID in the existing conversation owner, shared by list and dialog and cleared with conversation scope. Once `decision_recorded`, `approved` or `rejected` has been observed for that ID, a later stale `pending` summary/detail cannot erase recording truth, restore decision buttons or trigger automatic reopening. Confirmed terminal evidence takes precedence over recorded evidence; recorded evidence takes precedence over pending. Keep existing deadline/outcome handling, and never infer recording solely from locally reaching a deadline or from expired/cancelled status. Reopening history must show the retained authoritative status. Preserve this evidence when the dialog unmounts; use existing typed status/date fields, without a new backend revision or acknowledgement contract. Test recorded submit → stale pending list/detail → manual reopen, and uncertain submit → recorded poll → stale pending poll.

4. **Quiet normal sends and reveal timestamps (AT-036, AT-027).** Remove `Sending` at the live normal-bubble status mapping while keeping useful unconfirmed/failure/retry states and queue behavior. Use each message's actual `createdAt` with browser-local `Intl.DateTimeFormat` (include date and seconds for an exact readable instant). Propagate `AssistantReplyViewModel.createdAt` through both durable-reply branches of `mergeTurnModels` into `ProductionConversationTurnModel` and `TurnMessage`; timestamp and displayed reply must share identity. Tap/click/focus reveals its timestamp for about three seconds, then a brief CSS fade; repeated activation restarts the timer and unmount clears it. Use an accessible focusable trigger and Enter/Space operation without wrapping rich message links/buttons in another button or interfering with selection. Keep time available to assistive technology and honor reduced motion. Invalid/missing timestamps are omitted, never replaced with now or another message's time. A raw activity projection without a durable reply may lack a time; an available durable reply must show its own exact time immediately, including after reload.

   Preserve the existing generic “Doing an activity” / “Finished an activity” copy. Only entries whose existing activity kind is `terminal` use command-specific copy: “Running a command” while active and “Run a command” when completed.

5. **Prove and deliver the focused pass.** Extend existing tests only for the changed risk boundaries below; use production Home integration for layout acceptance, with debug frames as shared-component regression coverage. ## Likely touched surfaces, risks and rollback

Expected implementation: `apps/web/app/home/conversation-frame.tsx`, `conversation-frame-primitives.tsx`, `conversation-frame.module.css`, `conversation-approvals.tsx`, `conversation-frame-model.ts`, `home-workspace.tsx`, adjacent existing tests and Home-smoke test. Touch `conversation-presence.tsx` only if the verified root cause requires it. No Cloud generated contract edits, new dependency or general state framework is planned.

Main risks: moving active activity can mis-anchor approvals; dialog/list refetch can reopen stale state; new scrolling can fight manual history reading; timestamp triggers can harm rich-content interaction; style changes can affect other sheet callers. The identity/state tests and real-browser checks above are the release basis. Keep the diff near the repository's 200–500-line target where feasible; reassess independent scope if it grows, without dropping safeguards.

Assumptions/open limits: manual dismiss remains allowed by existing behavior; message-only approval identity cannot distinguish retry ordinals; missing loaded history uses the honest fallback. Authoritative durable-reply timestamps are available in the current public client and are part of this implementation. These are implementation constraints, not invented backend decisions. Escalate only if inspected public behavior contradicts the chosen durable state semantics.

Rollback is a focused revert of this UI change on its feature/PR branch. There are no data migrations or backend dependencies to roll back. Keep durable approval state and queue keys server/client-owned under their existing contracts; do not reset persisted user data. Preserve the isolated worktree while the PR is open.
