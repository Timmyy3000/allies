Stale execution recovery

Retire expired lease state during the next claim transaction, replay only eligible current-generation work proven not to have been dispatched, and let later same-profile work progress without introducing another service.

Feature overview

Problem

An expired active or stopping lease remains covered by profile uniqueness, so later queued work is skipped indefinitely when an immediate runtime failure or stopped request is lost.

Users

People waiting for a later turn with the same Ally, and operators responsible for durable recovery after a runtime or Hermes disconnect.

Outcome

The next claim pass retires expired state transactionally. Only eligible current-generation pre-dispatch work is requeued; ambiguous, cleanup-pending, and retired-generation work stays non-claimable.

Evidence: the work brief; engineering and continuity docs; accepted Nabu continuity, streaming, decision-log, and Hermes/Fly notes; current claim, lease, event, worker, and delivery code; and a staging trace with one dispatch, 86 partial deltas over about 8.4 seconds, no terminal event, and an expired lease.

Scope

Included

  • Bounded PostgreSQL reconciliation at the start of the existing claim transaction.
  • Classification by dispatch/session evidence, generation, and cleanup state.
  • Release or fencing of every expired unresolved blocker, including retired-generation leases.
  • Idle claim backoff from 1 to 10 seconds with bounded jitter and reset after a claim or recovered transport.
  • Focused concurrency, failure, ordering, restart, backoff, and documentation work.

Deferred or excluded

  • No Redis, queue service, scheduler, reaper, dependency, or API version change.
  • No SSE replacement, Cloud or Interface behavior change, or FND-009 idle stop/wake.
  • No message.delta coalescing in this PR.

Why coalescing waits

The adapter forwards validated deltas in order, caps text at 16 KiB, reserves 512 nonterminal positions, and uses bounded delivery batches. The 86 observed deltas did not exhaust those limits. A timed buffer adds ordering-sensitive async state without evidence that event pressure caused this incident.

Authoritative boundary: Foundry and PostgreSQL own durable execution truth. execution.dispatched is the replay boundary; a session mutation without that event is still ambiguous and must not replay.

Assumptions

  • Foundry remains owner of executions, attempts, leases, ordered events, and delivery outbox rows; PostgreSQL locks and constraints remain the production concurrency boundary.
  • Unknown Hermes outcome becomes terminal AttemptStatus.UNKNOWN, ExecutionStatus.FAILED, and a safe execution.failed. AttemptStatus.FAILED remains for positively reported runtime failure.
  • cleanup_pending and retired-generation work is never made claimable by reconciliation.
  • The latest brief intentionally changes older documentation that required a stopped acknowledgement or confirmed Machine retirement before reclaim; implementation updates local docs and canonical Nabu notes after acceptance.

Contract and state changes

No HTTP request, response, or event schema changes. Existing POST /api/v1/runtime/claims gains an internal pre-claim reconciliation side effect. A one-step constraint migration reserves sequence 100001 for server-owned terminal recovery while runtime-authored events remain capped at 100000.

Reconciler invariants

  • Run after Workspace lock and validation, before candidate selection, so requeued older work participates in ordered selection.
  • Process at most MAX_AVAILABLE_SLOTS oldest expired unresolved blockers per claim.
  • Use Workspace as the authoritative serialization row, then follow existing Workspace to Attempt to Profile to Lease ordering where rows exist; recheck expiry, generation, cleanup, and terminal state under lock. Do not broadly refactor unrelated writers.
  • Use a narrow server-owned append seam: fixed lease-expiry reason, existing payload validation, stable event and stream identity, next attempt-local sequence including high prior sequences, and no runtime token.
  • Write event, outbox, attempt/execution state, and lease release in one outer transaction. Failure rolls back all effects; stable identity and terminal checks make retries no-ops.
1. Lock and validate Workspace.
2. Lock Attempt, Profile, then Lease and recheck state.
3. Requeue only eligible work; otherwise fence or append one safe failure atomically.
4. Select the next candidate from refreshed durable state.

Simplest viable approach

Use the existing claim endpoint as the durable wake-up path. If no runtime is running, PostgreSQL retains safe durable state and recovery waits for restart and the next claim. Add one transaction-local reconciler and one narrow synthetic-event helper in the existing backend runtime service layer, reuse current models, locks, payload validator, and outbox behavior, and retain the immediate runtime fail request as the low-latency path.

Keep backoff in FoundryWorker._run_loop. Use standard-library randomness, a 1-second floor and 10-second ceiling, and injected or patched timing in tests. Empty claims progress through 1, 2, 4, 8, and 10 seconds with bounded jitter. A claimed execution or first successful response after retryable transport failure resets the delay. Remove the production 250 ms override.

Phases

1. Reconcile stale truth

Goal: clear expired blockers without replaying ambiguous Hermes work.

Work: serialize on Workspace, follow Attempt to Profile to Lease order, classify dispatch/session, generation, and cleanup state, then atomically requeue eligible work or use the server-owned append seam and release/fence the lease.

Files: backend/runtime/services/claims.py and focused additions to test_fnd005_backend.py, test_fnd007_execution.py, and test_services.py.

Exit: eligible pre-dispatch work is claimable; ambiguous work fails once; cleanup and retired-generation work never requeues; an empty no-successor claim still reconciles; concurrent claimers do not duplicate effects or regress lock ordering.

2. Add idle backoff

Goal: reduce idle traffic without changing active-turn responsiveness or transport semantics.

Work: implement bounded-jitter 1, 2, 4, 8, 10 progression; reset on claim and transport recovery; retain immediate slot refill; remove idle_delay=0.25.

Files: runtime/allies_runtime/foundry.py, runtime/allies_runtime/__main__.py, runtime/tests/test_foundry.py, and runtime/tests/test_composition.py.

Exit: deterministic tests cover floor, ceiling, growth, reset, retry, stop, and free-slot behavior; a restarted continuously polling runtime reconciles within the 10-second ceiling.

3. Validate and document

Goal: preserve continuity contracts around the recovery change.

Work: run focused and complete validation; update docs/architecture/foundry-continuity.md and runtime/README.md; after acceptance, revision-safely update canonical Nabu continuity and streaming notes.

Exit: renewal, stopped acknowledgement, generation fencing, order/delivery, immediate failure, session compare-and-set, and coverage pass; docs describe the new expiry and restart rules.

Acceptance criteria

  1. Each claim reconciles bounded expired unresolved active or stopping blockers across current and retired generations before candidate selection.
  2. Eligible current-generation predispatch work requeues; cleanup-pending and retired-generation work remains non-claimable.
  3. Dispatch or session checkpoint expiry atomically marks attempt unknown and execution failed, releases the lease, appends exactly one ordered failure event, and never replays.
  4. Dispatch plus partial deltas plus omitted runtime failure is recovered later and the next same-profile execution becomes claimable.
  5. Concurrent claimers lock Workspace then use Attempt to Profile to Lease order, produce one outcome and one event/outbox pair when required, and at most one replacement lease. Existing transaction tests cover race and deadlock sensitivity.
  6. Immediate failure reporting, claim idempotency, profile serialization, generation fencing, session compare-and-set, ordered delivery, and SSE remain unchanged.
  7. Idle polling uses bounded jitter over the exponential 1-to-10-second progression and resets on claim or transport recovery; active free slots refill promptly.
  8. No service, dependency, Redis use, table, API version, Cloud/Interface change, or FND-009 work is added; migration 0014 only widens the event-sequence check by one reserved server terminal slot.
  9. An empty claim without a successor still reconciles. With no running runtime, recovery waits safely for restart; continuous polling then reconciles within the 10-second ceiling.

Risks, rollback, and open decisions

  • Old stream overlap: expiry release can overlap a truly stuck Hermes stream. Keep renewal-loss cancellation and late-write fencing, wait the full 60-second expiry, and prove the old token cannot mutate durable state. The brief accepts progress after expiry; reviewers must confirm this behavior change.
  • Duplicate events or deadlocks: mitigate with Workspace serialization, established Attempt to Profile to Lease order, state rechecks, stable synthetic identity, atomic commit, and focused concurrent transaction coverage in existing tests.
  • Half-reconciled state: event creation and enqueue stay in the same transaction, so validation or persistence failure rolls back release.
  • Flaky jitter tests: patch randomness and sleep, assert ranges and transitions, and keep production bounds constant.
  • Rollback: revert application code and docs while retaining the backward-compatible widened sequence constraint. Committed failure events and released leases remain durable facts and must not be deleted or replayed. No dependency rollback is needed.
  • Open decisions: none for implementation. Coalescing is a measured follow-up only when delivery or database evidence shows bounded one-for-one forwarding is a material bottleneck.
