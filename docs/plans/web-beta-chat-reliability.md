## Approach and contracts

Keep fixes at current ownership boundaries: transfer manager owns local recovery; the files hook owns draft ingestion; the composer forwards dropped files; the frame model derives presentation from matching Cloud identities; approval queries own read retry/error presentation. Add only narrow helpers needed to share these rules and test them. No new dependency, global event bus, or parallel state machine.

| Boundary | Required contract |
| --- | --- |
| File ingestion | Validate the whole proposed batch, including existing attachments, through `validateSelectedFiles` before committing selection. Failure preserves the previous draft; picker, capture, reselect, and drop use the same limits. Do not upload until Send. |
| Persistence | Resolve only after transaction completion. Distinguish application capacity, browser quota, unavailable/security-denied storage, and other read/write/abort errors; expose actionable safe copy, never raw exceptions. Failed preparation makes no reservation and preserves composer text/files. Reopening storage after failure must be possible. |
| Cleanup | Reclaim only records proven disposable: ready records whose matching Cloud message has been claimed/progressed, or explicitly discarded/consumed recovery records. Never infer disposal from age, `failed`, or `cancelled` alone; cancelled text/files are recoverable intent. Preserve unclaimed ready transfers, interrupted work, and unknown legacy records. No cross-account inspection or deletion. Recheck limits transactionally after safe cleanup. |
| Turn presentation | File hashing/persistence/reservation/upload/inspection is not Ally work. Failed/rejected preparation has no Thinking or thinking avatar unless another accepted turn is actually active. Claimed/running evidence for the same turn overrides a stale wake hint. Preserve accepted text-only waiting behavior and completed-but-not-yet-visible reply continuity. |
| Durable success | Match conversation, source message, and turn ordinal before resolving status. A completed durable message/reply or delivered legacy reply wins over stale local transport/projected failure. Keep genuine current Cloud failure/stopped/truncated outcomes visible; partial streamed text alone is not proof of successful completion. Render each reply once across refresh/reconnect. |
| Approval polling | Keep last valid summaries/details while transient reads retry. Reuse session authentication recovery; do not retry terminal access denial as network failure. Disable/hide scoped approval UI immediately on lost access. Preserve decision choice/key, duplicate-tap protection, expiry, acknowledgement deadlines, and server authority. |

## Implementation sequence

1. **Isolate the reported failure, then unify ingestion.** Before implementing the size fix, reproduce a supported multi-file batch totaling about 2.5 MB and trace actual `File.size` values through selection validation, IndexedDB transaction completion, serialized reservation manifests, and Cloud response. Record the first failing boundary and a sanitized error class/status/code, never file contents or private names. Add a regression at that boundary before fixing it. If only mocked/local success is available, report that coverage and leave the deployed symptom unverified; a server-only failure is a scoped dependency to report, not permission for backend changes. Do not loosen limits or claim the symptom fixed from validator tests alone. Extend the files hook with one batch-add path and wire a typed files callback through frame/composer. Use actual byte sizes, preserve the old selection on batch rejection, and release only newly rejected previews. Cover exact/over count and byte limits, empty files, unsupported names/types, and existing selections.

   While the conversation frame is mounted, install page-level file `dragover`/`drop` navigation suppression, including outside the composer and when attachment actions are disabled; remove listeners on unmount. Only the enabled composer accepts files. Detect file drags with `DataTransfer.types` containing `Files`; ignore text-only drags. On drop, synchronously snapshot file-kind `items` via `getAsFile()` (fallback to `Array.from(files)` only when items are unavailable). Reject the whole batch for a directory entry, null/unreadable file item, or invalid file; never recursively enumerate folders. Where directory inspection is supported, use its directory flag; otherwise reject non-readable/zero-byte candidates through the same validation without claiming folder support. For mixed text/files, process file items only and never insert accompanying text. Outside/disabled drops attach nothing and announce where files can be added or that attachments are unavailable. Use composer drag depth to avoid child-boundary flicker; reset on drop, true frame leave, drag end, Escape, scope change, and unmount. Reuse composer styling for a visible “Drop files to attach” affordance and polite live announcements for acceptance/rejection; retain the keyboard-accessible picker as the equivalent path.

2. **Repair bounded draft storage and recovery.** Give the existing storage adapter classified failures and robust open/transaction failure recovery. Before rejecting admission for per-Ally or database capacity, reconcile eligible current-scope terminal records with existing Cloud observation and delete only proven disposable records. Keep byte/count checking plus deletion/write atomic where they share a transaction; do not await network work inside an IndexedDB transaction. Revalidate eligibility against the transaction's current record and preserve records another tab has changed. A failed erase must not be reported as cleanup success. Keep persistence-before-reservation, idempotency keys, upload-generation handling, and cancellation races intact. An unavailable store leaves files/text editable, removable, and retryable; do not silently send without durable draft storage. If cancelled recovery consumption needs a persisted marker, make it optional and treat missing legacy markers as recoverable; never mark consumption merely because it was copied into volatile composer state.

   Map storage events explicitly, settling each operation once:

   | Evidence | Classification and recovery |
   | --- | --- |
   | Deliberate cap abort | `capacity`; preserve the deliberate cause through `onabort`; offer finish/discard saved work. |
   | Missing IndexedDB, synchronous `open` `SecurityError`/`NotSupportedError`, equivalent open-request error | `unavailable`; explain browser storage is unavailable, suggest retry or a storage-enabled window without asserting private mode was detected. Clear the cached open promise. |
   | `QuotaExceededError` on request, transaction, or synchronous write | `quota`; preserve drafts and suggest freeing browser storage then retrying. |
   | `open.onblocked`, or open unresolved after 5 seconds | `blocked`/`unavailable`; settle with close-other-tabs/retry guidance and clear the cache; close any late successful connection rather than caching it. |
   | Connection `versionchange` or unexpected close | Close/invalidate the cached connection; in-flight failure remains visible; next explicit retry opens afresh. |
   | Request `error`, transaction `error`/`abort`, synchronous transaction/clone/write exception | `transaction`, unless a known capacity/quota/unavailable cause exists; preserve cause, report save/read/remove failure accurately, reset a broken connection, and allow explicit retry. |

   Observe request errors and transaction completion separately: a successful `put` request is not a committed save. No automatic write retry, store deletion, or schema recreation on failure. A minimal injected open/factory boundary inside the existing adapter is allowed for deterministic event tests; retain real-browser success, reopen, and concurrent admission checks.

3. **Make chat presentation consistent.** Remove reservation-phase copy while retaining thumbnails, meaningful upload progress, and recovery controls. Reuse the existing toast visual/live-region treatment for attachment action errors and persistent approval read errors, with dismissal and duplicate suppression; retain durable failed-file status and Retry/Remove/Cancel affordances. Derive Thinking/wake/avatar and message/turn status from the same matching accepted/claimed/durable evidence in `home-workspace.tsx`, `conversation-frame-model.ts`, and `conversation-frame.tsx`. Cover rejected preparation, malware rejection, an unrelated active turn, claim while wake hints lag, delivered success plus stale failure, true partial failure, and legacy/durable reply deduplication.

4. **Bound approval read retries.** The session operation owns the entire per-read retry budget: one initial request plus at most one repeat, whether triggered by auth recovery or transient failure. `apps/web/lib/session/web-session.ts` currently retries only typed network/timeout failures, immediately; it has no retry-delay or Retry-After support. Extend its existing `retryTransient` option compatibly from boolean to `boolean | "approval-read"`. Only approval summary/detail reads select the new mode, which recognizes existing typed network, timeout, throttled (429), server (5xx), and status 408 errors and waits a fixed 1,000 ms before its one transient repeat. The wait must abort on caller cancellation and check session generation before reinvocation. Boolean true retains today's immediate network/timeout retry; false/omitted and all existing authentication/CSRF behavior remain unchanged. No Retry-After propagation or shared Cloud contract change is planned. Auth recovery consumes the same two-invocation budget and does not add the transient delay. Set query retries to false; do not wrap session retries in another retry loop. Summaries and details share this policy, with non-overlapping three-second poll cycles. Preserve signal cancellation and session-generation fencing. Classify outcomes as follows:

   | Read outcome | Behavior |
   | --- | --- |
   | First 401 | Existing session recovery, then at most one repeat; no interim error UI. A second 401 invalidates access immediately, hides cached approval UI, and stops reads. |
   | Network, timeout, 408, 429, or 5xx | One session-owned repeat after the new fixed 1,000 ms delay; retain cached data. After three exhausted consecutive cycles, show one retry toast per failure episode. Do not schedule overlapping interval/retry requests. |
   | 403 | No retry; immediate access handling, hide scoped approval UI and stop reads. |
   | 404 | No retry; mark requested approval/conversation unavailable, disable decisions and stop polling that resource; one actionable notice. Do not treat a missing detail as approval success. |
   | Other 4xx, schema/contract error | No retry; disable affected decisions, one actionable notice, pause that resource until explicit refresh or scope change. Never substitute fabricated data. |
   | Abort from scope change/unmount | No retry, failure counter, or toast; discard late results. |

   A last good detail remains visible during recoverable failure but cannot authorize a decision until a successful current-scope detail read clears that failure. A normal background refresh alone does not disable a still-valid detail; expiry, permission loss, unresolved failure, or decision-in-flight does. No data means a loading/retry state and no actions. Terminal details remain terminal despite stale pending summaries. Reset failure count/toast suppression on successful read or resource/scope identity change, and clear on access disablement/unmount; manual Retry consumes one new bounded cycle without resetting the failure episode until success. Preserve decision-write failure's explicit same-choice/key retry, expiry and acknowledgement rules; read recovery never resubmits a decision.

5. **Validate and deliver the single coherent change.** Run focused tests, required checks, production-browser attachment/state cases, then separate simplicity and correctness reviews. Keep tests beside each change; avoid unrelated cleanup even if the combined diff exceeds the normal size target. The explicit one-PR choice governs; explain size if it exceeds 1,000 non-generated lines. Delivery remains one PR to `dev` with current-head CI/review monitoring; no merge or deployment is implied by this plan.

## Risks, rollback, and open decisions

- The precise reported small-file failure is unproven. First implementation evidence must isolate invalid size/empty-file input, storage failure, or server response; limits must not be loosened to mask it.
- Cleanup is the highest data-loss risk. Default to retention whenever Cloud confirmation, scope, or consumption is uncertain. Storage can remain full of legitimate retryable work; accurate recovery/discard guidance is the correct result then.
- Durable content can coexist with genuine execution failure. Success precedence is limited to proven delivered/completed evidence; do not classify arbitrary partial text as success or overwrite Cloud data.
- The three-failed-poll-cycle toast threshold is a proposed implementation default, not a new product contract; independent review may adjust it while keeping retry bounded and errors actionable. No unresolved product decision blocks implementation after review.
- No database version bump, limit change, or server migration is planned. Rollback reverts the web changes; never wipe IndexedDB as rollback. Optional additive recovery metadata must remain readable by the old client. Any safe cleanup already performed is irreversible locally, so only redundant durable/explicitly discarded records may be reclaimed.
