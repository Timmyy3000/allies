Mobile Google auth and personal account

Make native auth one reusable session seam.

INT-008 turns the mobile session placeholder into secure Google sign-in, restoration, profile and avatar editing, and personal Workspace access. Mobile owns native lifecycle; Cloud remains the durable authority.

Ready for implementation

The contract is merged into Cloud dev. Staging enablement, exact app-return registration, and a real iOS/Android dev build are release gates for live proof.

Nabu source

projects/allies/engineering/specs/interface/INT-008-mobile-google-auth-and-account.md

Implementation surface

apps/mobile + packages/cloud-client

Current baseline

Expo SDK 57, Expo Router, TanStack Query, typed Cloud client

Release implication

Native dependencies, app links, or config require a new EAS build

Recommendation: extend the shared typed Cloud boundary with the native auth contract, then wrap it in a small mobile session adapter. Store only the rotating opaque refresh token in SecureStore; keep access credentials, PKCE state, and one-time codes in memory; let TanStack Query own account data.

What the repository says today

The existing seams make this a focused vertical slice, but the mobile auth provider is intentionally still a placeholder.

Delivery

The adapter is the only owner of credential lifecycle. Account screens consume view models and do not know how a token was obtained.

Scope is intentionally narrow

The goal is account access, not the next product surface. Ally creation, conversations, and provider credentials stay outside this slice.

In scope

Native account access

  • Expo Router public/authenticated route groups and a native sign-in entry.
  • Expo AuthSession/system-browser Google flow with PKCE S256, app-link return, state verification, cancellation, and retry.
  • SecureStore-backed refresh rotation, in-memory access credentials, restore, serialized refresh, revocation, and logout cleanup.
  • Current account, display-name edit, avatar pick/upload/complete/read/delete, personal Workspace, and offline/retry states.
  • Safe areas, keyboard, system back, screen-reader labels, touch targets, reduced motion, and privacy-safe errors.
Out of scope

Do not broaden this increment

  • WebView or browser-cookie emulation, direct Google token handling, or client-side provider credentials.
  • Biometrics, device attestation, push, offline mutations, account switching, or pre-auth transfer.
  • ChatGPT sign-in, team Workspaces, Ally creation, conversation streaming, and runtime execution.
  • A new global store for credentials, account DTOs, or server state.
  • Live device proof before Cloud staging deployment, native enablement, and redirect registration exist.

State model and data ownership

Each state has one owner and one recovery path. That keeps the UI truthful without introducing a second global state system.

Sign-in attempt

One attempt, one verifier, one outcome

  1. idle → opening browser → waiting for return → exchanging.
  2. Cancellation returns to idle without persisting anything.
  3. State mismatch, expired flow, replay, timeout, or provider unavailability discards the attempt and offers a fresh retry.
  4. Do not reuse a verifier, state, or one-time code after any terminal attempt result.
Bootstrap and refresh

Do not claim signed-in too early

  1. checking storage → refreshing when a refresh token exists.
  2. Only a validated Cloud response becomes signed-in.
  3. Network failure with a still-present session becomes offline-with-session; expose retry without deleting usable local refresh state.
  4. 401/session-invalid clears SecureStore, access memory, account queries, and protected routes.
Ownership

Keep data in the narrowest useful layer

  • Session adapter: access token, refresh rotation, lifecycle generation.
  • SecureStore: current opaque refresh token only.
  • TanStack Query: account, profile/avatar, and Workspace data/cache.
  • React local state: form text, focus, upload progress, retry intent.
  • Zustand: no credentials or account DTOs; only add it if a real cross-screen workflow appears.
Logout and revocation

Local cleanup is unconditional

  • Attempt Cloud logout with refresh and bearer when available.
  • On success, 401, timeout, or network uncertainty, clear local credentials and Query caches.
  • Never retry a rotated refresh token or expose raw logout failure details.
  • Return to public sign-in/onboarding with a clean session generation.

Acceptance criteria

These are observable outcomes, not implementation tasks.

  1. Google sign-in uses the system browser and Cloud-owned callback; no WebView, browser-cookie emulation, or direct Google token exchange exists.
  2. PKCE uses a random verifier, unpadded base64url S256 challenge, exact registered redirect, and one-time in-memory state.
  3. Only the current opaque refresh token is persisted in SecureStore; access token, verifier, state, code, URLs, logs, analytics, and crash payloads stay out of durable storage.
  4. Refresh rotation is serialized; the new token is securely written before the old one is discarded; SecureStore failure never becomes signed-in.
  5. Revocation, logout, 401 session invalidation, and uncertain logout clear local credentials, memory, Query caches, and protected navigation.
  6. Bootstrap distinguishes checking storage, refreshing, signed-in, signed-out, offline-with-session, and unavailable; the UI never claims signed-in before Cloud validation.
  7. Mobile can view and edit the current profile, manage avatar lifecycle through signed object-storage instructions, and load the personal Workspace.
  8. Profile/avatar/Workspace requests use the shared typed Cloud boundary and bearer allowlist; object-storage upload receives exact signed headers and no bearer.
  9. Loading, canceled, retryable, offline, unauthorized, throttled, provider-unavailable, and privacy-safe error states are explicit on native surfaces.
  10. System back, safe areas, keyboard dismissal, screen-reader labels/focus order, touch targets, reduced motion, and narrow iOS/Android layouts are verified.
  11. Vitest covers pure PKCE, redirect validation, SecureStore port, refresh coordinator, session reducer, response mapping, profile schema, and error policy; no broad new test framework is added without evidence.
  12. Full validation and real Android/iOS dev-build evidence are recorded, and the release/README/Nabu handoff identifies whether the result is native-build-required or OTA-compatible.

Architecture decision

The recommendation is based on the existing repository seams and the security requirements in AUTH-002.

Recommended · shared contract + mobile adapter

One typed API boundary, one native lifecycle owner

  • Reuses the existing Cloud client, response mappers, transport limits, and error taxonomy.
  • Keeps SecureStore and PKCE concerns in mobile where platform lifecycle belongs.
  • Prevents account screens from duplicating auth, refresh, or token policy.
  • Costs a contract snapshot update plus a small adapter and explicit route/config work.
Rejected · mobile-specific fetch layer

Fast first request, duplicated contract risk

  • Would duplicate envelope parsing, account mappers, error rules, and future OpenAPI changes.
  • Makes web/mobile semantics drift more likely and hides the current shared transport seam.
  • Does not reduce the native lifecycle work, because PKCE and SecureStore still belong in mobile.
Rejected · browser cookies or WebView

Conflicts with the native contract

  • Does not provide the required bearer/native session semantics.
  • Creates lifecycle, privacy, callback, and logout ambiguity.
  • Would make device proof appear to work while bypassing the acceptance contract.
Design constraint

Prefer the smallest vertical slice

  • Do not introduce a generic auth framework or global store for one provider.
  • Do not add a second avatar renderer; compose from the native feature surface.
  • Keep each new dependency justified by a concrete SDK 57 platform requirement.

Risks, mitigations, and rollback

The safest rollback is feature disablement and local cleanup, not a partial fallback to browser auth.

Risk register
RiskSeverityMitigation / rollback
Callback works in Expo Go but fails in a real buildHighUse custom dev builds with exact schemes/claimed links; test cold return and background/foreground. If broken, keep native auth disabled and preserve public onboarding.
Refresh rotation race loses the current sessionHighSerialize refresh, write the new SecureStore token before replacing memory, and test concurrent 401s. On write failure, fail closed rather than persisting a stale token.
Cloud staging is merged but not enabledMediumUse fixture/transport tests; show unavailable/retry; do not invent a browser fallback. Enable only after deployment and flag verification.
Avatar direct upload leaks bearer or uses stale signed headersHighKeep object-storage PUT outside the authenticated API wrapper, send only exact signed headers, and treat expiry/retry as a fresh prepare step.
Account data remains in cache after logout/revocationHighOne session-generation cleanup path clears SecureStore, memory, Query cache, and protected routes on every terminal local sign-out.
Native dependency/config changes are shipped as OTAMediumClassify release changes. Bump app version and create a new EAS build for native changes; publish OTA only after the compatible runtime exists.

Rollback: turn off native auth at the Cloud flag/config boundary, leave the mobile routes behind an unavailable state, clear any locally stored native refresh token during the next app start, and ship a compatible JavaScript update only if the installed runtime supports it. Do not route users through browser-cookie auth as an emergency substitute.
