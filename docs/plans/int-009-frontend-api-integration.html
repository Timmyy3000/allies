Browser security topology

The API contract uses host/path-scoped cookies. A web facade keeps that contract usable without exposing the HttpOnly capability or manufacturing forbidden browser headers.

HopBehaviorInvariant
Onboarding browserWaitlist client requests the exact /api/v1/waitlist/* path on the current Interface origin with credentials: include. The facade preserves the path-scoped csrftoken; the browser adapter never reads the capability cookie or needs to read a cookie outside the onboarding document path.Browser supplies normal Origin/Referer; client does not set Origin.
Next route handlerForward the method, body, Cookie, Origin, Referer, Idempotency-Key, Content-Type, and Accept to the configured Cloud origin, deriving X-CSRFToken from the incoming csrftoken cookie.Same path means Cloud /api/ and /api/v1/waitlist/ cookie paths remain valid on the browser origin; no request body is invented.
Cloud responseReturn status, JSON envelope, safe content headers, and all Set-Cookie values to the browser.Capability stays HttpOnly; CSRF remains readable only for the exact mutation header; no cookie/value is logged or copied into app state.
DeploymentCloud's ALLIES_TRUSTED_ORIGINS must include each actual Interface origin. Web uses explicit NEXT_PUBLIC_WAITLIST_ENABLED and NEXT_PUBLIC_WAITLIST_CONSENT_VERSION.Feature is default-off and join fails closed if consent is absent; staging 503 remains an honest unavailable state.

Contract boundary

These operations are present in the pinned staging OpenAPI. Generated types remain the source for request and response shapes; the browser sees the same paths through the web facade.

OperationRequest shapeClient behaviorImportant outcomes
GET /api/v1/waitlist/sessionNo body; browser credentials included.Bootstrap the anonymous capability. Do not persist the capability in application storage.204 sets the HttpOnly capability and path-scoped csrftoken cookie.
POST /api/v1/waitlist/draftNo body; browser credentials included.Create or resume the anonymous draft; capture the authoritative acknowledgement, then restore.Do not send the older handoff's {}; handle unavailable/throttle explicitly.
GET /api/v1/waitlist/draftNo body.Reconcile after bootstrap, refresh, stale revision, or a successful mutation.Lifecycle and revision control the UI state.
PATCH .../configuration{ revision, changed fields }Send only changed values with CSRF and a stable idempotency key.Limits: name 80; appearance key 128; job/personality 1200.
POST .../greeting{ revision }Request only when configuration is ready; expose pending generation.Keep model output as untrusted plain text; handle 503/429.
POST .../reply{ revision, exact text }Show sending, then pending only after acknowledgement; never claim live execution.Reply limit 4000; preserve exact input on failure.
POST .../join{ revision, email, active consent_version }Submit once with stable idempotency; keep Ally and preview visible.Show masked email; email limit 254; no credentials stored.

Waitlist mutations use credentials: include, X-CSRFToken derived by the same-origin facade from the path-scoped csrftoken cookie, a trusted browser origin context, and a stable Idempotency-Key. Existing auth requests retain their separate csrf_token behavior until that contract is revised. Retry the same intent with the same key; do not silently mint a new key.

Cloud-owned snapshot

  • Draft id, lifecycle, revision, configuration, greeting, pending reply, join state, timestamps.
  • Returned after restore and after every successful mutation acknowledgement.
  • Controls refresh restoration and stale-revision reconciliation.

Browser-owned interaction

  • Current step, focus, open/closed panels, unsaved form input, mutation status, and retry intent.
  • Use one in-flight guard and one in-memory idempotency key per visible operation; no general queue or second general-purpose store.
  • No localStorage/sessionStorage for draft, email, reply, or capability.
  • Greeting and reply text render as plain text, never executable markup.

Risks and fallbacks

The plan keeps uncertainty visible and preserves a safe stopping point.

RiskLevelMitigation / fallback
Staging contract can change while this branch is in flight.MediumKeep the fetched snapshot and metadata together, run bun run cloud:check, and refresh only through the repository fetch script with reviewable generated diffs.
Staging waitlist session is currently unavailable.MediumA read-only probe returned 503 from the staging session endpoint. Keep fixture and transport coverage authoritative for CI, and make live smoke evidence conditional on the environment becoming available.
Older UI branch conflicts with current Cloud/session foundation.HighSelective file import and focused conflict resolution. Never accept branch deletions of generated client, auth, environment, or root guidance without explicit review.
CSRF cookie is host/path scoped and cannot be read from a direct cross-origin page.HighUse the exact same-origin /api/v1/waitlist/* facade; preserve upstream Set-Cookie paths; test session bootstrap, cookie storage, forwarded headers, and mutation header preparation.
Trusted origin is absent, the web feature is enabled without consent, or the feature flag is disabled.HighKeep the feature default-off and leave the static story in place with no Cloud call when disabled. Require explicit NEXT_PUBLIC_WAITLIST_CONSENT_VERSION; missing consent disables only join and never exposes configuration details. Document the local/staging/production ALLIES_TRUSTED_ORIGINS matrix.
Older UI branch reintroduces sign-in or mismaps shape/color/personality.HighExclude sign-in components, route CTA to waitlist bootstrap, and use explicit v1 appearance/personality serialization fixtures.
Replies or email expose more than the safe Cloud snapshot.HighAllowlist the confirmed fields only, require masked join email, preserve plain-text output, and reject/ignore unknown fields.
Retries duplicate a mutation or create a new intent.MediumGenerate one idempotency key per user intent, persist it only in in-memory mutation state, serialize operations, reuse on retry, and re-read after acknowledgement.
Greeting becomes stale after configuration edits.MediumInvalidate only when name, job, or serialized personality changes; appearance-only edits do not invalidate it. Trust the post-ack snapshot and Cloud lifecycle before showing it again.
UI implies the reply was delivered or executed.MediumUse pending language and assertions; keep the Ally, greeting, and attempted reply visible after join without claiming runtime execution.
Existing PNG import prevents the web baseline from typechecking.MediumAdd the smallest repository-local asset declaration or supported import path as part of the UI baseline, then record the fix in web typecheck evidence.

Acceptance and verification

Evidence should be attached to the branch and PR, with contract availability called out separately.

  • CTA enters the first Ally flow from the existing /onboarding route.
  • When waitlist enablement is false, the static story remains present and no Cloud request is made; missing consent disables only join.
  • Ally/avatar and story remain responsive from 320px through 1440px.
  • Keyboard order, focus visibility, touch targets, labels, and screen reader state are usable.
  • Reduced-motion mode removes non-essential choreography without losing meaning.
  • Bootstrap, create/resume, restore, save, greeting, reply, and join have explicit loading/error states.
  • Waitlist calls use the same-origin /api/v1/waitlist/* facade; cookies, Origin/Referer, CSRF, and idempotency behavior are covered without manually setting Origin.
  • Stale revision restores the draft before another mutation; unsaved input is preserved.
  • Reply is sending first and pending only after acknowledgement; no direct provider/runtime call exists.
  • Join shows a masked email and keeps the Ally, greeting, and pending reply visible.
  • No sign-in or authenticated account flow is reachable from the waitlist CTA; join is disabled when consent configuration is absent.
  • Snapshot mapping allowlists greeting/reply/join fields and maps the local appearance/personality model to the Cloud request shape.
  • Appearance and personality serialization fixtures are deterministic, bounded, and covered; appearance-only edits do not invalidate a greeting.
  • Response limits, field errors, 404/409/422/429/503, idempotency conflict, and timeout paths are covered.
  • Cloud contract verification, typecheck, lint, tests, and web build are recorded.

Focused checks

  • Cloud client and facade tests for credentials, CSRF cookie/header, origin forwarding, revision, and idempotency.
  • Gateway/state tests using fixture responses for every lifecycle and error branch.
  • Vitest/Testing Library flow tests for refresh restoration, retry, pending reply, masked join, and accessible status/focus behavior.
