| Blocker | CSRF transport contract | **High confidence.** The plan cannot satisfy any unsafe Cloud request as written. It explicitly preserves `getCsrf(): Promise<void>` and limits the Cloud-client change to return-path validation, so no component owns the `X-CSRFToken` value returned by Cloud. The existing request preparer instead reads `document.cookie` on the Interface origin using `csrf_token`; Cloud sets its cookie on the separate Cloud origin under Django's default `csrftoken`, and the accepted INT-007 contract requires keeping the exposed response header in memory. It does not define the shared replay budget when the two failures occur in sequence, and the tests cover each mechanism but not `401 -> csrf_rejected` or `csrf_rejected -> 401`. Different implementations could perform a third mutation attempt or silently skip one stated recovery rule. | `docs/plans/int-007-web-google-auth-account.md:25`, `:66`, `:84`, `:174`, `:266`, `:297`, `:322`; `ENGINEERING_STYLE.md` AL-04, AL-05, AL-06, and AL-10. | Specify one operation-wide replay budget and the terminal behavior for compound failures. The safest contract is two total operation invocations: the first eligible auth or CSRF failure consumes the sole replay; any eligible failure from the replay is surfaced without another invocation. Add ordered compound-failure and concurrent-call tests with exact call counts. |
| Major | Direct avatar upload reliability | **High confidence.** The direct object-store PUT bypasses the controlled transport's 10-second timeout. ## Missing Questions

- What exact in-memory owner captures, rotates, and supplies Cloud's `X-CSRFToken` across the Cloud client and session executor without relying on an Interface-origin cookie?
- When a single operation encounters both an authentication failure and a CSRF failure, which failure may consume the sole replay and what state is returned for the second failure?
- What bounded timeout applies to the direct object-store PUT, and how is it distinguished from caller cancellation in UI recovery?
- What mechanism renews signed avatar read metadata while `/account` remains mounted across its expiry?

## Plan Feedback For Revision

- Add a concrete cross-origin CSRF token data path and tests before any unsafe-route implementation; this is required for the plan to become executable.
- Define a single shared replay-budget state machine, including compound auth/CSRF failures and exact invocation counts.
- Add timeout ownership and race tests for the raw object-store PUT.
- Add proactive signed-avatar renewal and long-lived-page expiry tests rather than relying on `staleTime` alone.
- Restore the accepted Zod display-name schema requirement using the existing dependency.
- Refresh the Nabu revisions and Cloud PR #13 status, leaving only deployment and staging configuration as external Google-flow blockers.

High - the findings are grounded in the accepted current Nabu spec, live merged PR status, the repository plan and policy, and the concrete Interface and Cloud transport implementations.
