# Adversarial Review

## Verdict

Blocked.

The plan has one blocker. It does not define a shared, trustworthy rate-limit
identity for a native client in the current Railway deployment. Do not enable
the native routes until this is resolved and proved in staging.

## Findings

| Severity | Area | Finding | Evidence | Recommendation |
| --- | --- | --- | --- | --- |
| Blocker | Security boundary and abuse control | The proposed native sign-in limit cannot work as described on Railway. Native endpoints must not use auth cookies, but the existing Railway identity is an HttpOnly browser throttle cookie. Without it, the existing helper returns no cache-backed identity and uses only a process-local admission bucket. That bucket does not provide a shared per-requester limit across workers or instances. | The plan requires shared-cache limits and the Railway admission guard for native begin, exchange, refresh, and logout (`auth-002-native-session-contract.md:385-387`, `:551-556`). It also states that native endpoints do not set cookies (`:204-207`). `auths/api/common.py:160-177` derives a Railway identity from the browser throttle cookie; `:227-252` is only a process-local gate. The Railway runbook states that the edge hides the client address and that the cookie is the browser fairness key (`docs/operations/railway-staging.md:103-110`). | Before implementation, select one native-safe, low-cardinality identity that is available at Railway and cannot be client-forged. Record its trust chain, key format, retention, and cache scope. Examples are a verified edge client-prefix header with an accepted proxy-trust contract, or a separately designed server-issued native admission credential. Add staging tests for missing, forged, rotated, and concurrent identities; shared-cache failure; and more than one web process. Keep native auth disabled if this proof is unavailable. |
| Important change | Provider protocol correctness | The plan requires separate browser and native Google callbacks, but it does not define the configuration change that makes this true. The current Google adapter overrides every `ProviderFlow.redirect_uri` with the single `ALLIES_AUTH_GOOGLE_REDIRECT_URI` setting on both authorization and token exchange. A new native callback would otherwise use the browser callback or require an unsafe global switch. | The plan calls for a dedicated native callback and for an explicit `ProviderFlow` callback (`auth-002-native-session-contract.md:165`, `:312-334`). The deployed configuration has one Google redirect value (`backend/config/settings.py:352`, `:568-575`), and `auths/providers/google.py:38` and `:137` prefer that value over the flow value. | Add an explicit callback-configuration design: exact setting names, the browser/native selection rule, production validation, and the Google registration matrix for local, staging, and production. Make the provider consume only the transaction-selected, allowlisted callback. Add a negative test that a browser transaction cannot use the native callback and vice versa. |
| Important change | Callback, cleanup, and error semantics | The native transaction state has only `consumed_at`, yet the plan requires a provider call outside long database locks and cleanup of expired records. It does not define what happens when Google returns denial or times out after the transaction is claimed, or when cleanup deletes an expiring transaction before the exchange code is written. This leaves cancellation, retry, and failure ownership ambiguous. | The proposed model has only nullable `consumed_at` (`auth-002-native-session-contract.md:275`); cleanup deletes expired native transactions and codes (`:187`, `:335`). The plan keeps provider I/O outside long locks (`:474-477`). Its callback function accepts only a provider code and state (`:181`), while the route also accepts provider denial fields (`:198`). The existing browser flow marks `consumed_at` before `verify_callback` (`backend/auths/services/flows.py:236-241`) and cleanup deletes expired flows (`backend/auths/services/cleanup.py:26-41`). | Define a terminal transaction state machine and cleanup rule. Include at least `pending`, `claimed`, `completed`, `denied`, and `failed` outcomes; the stored safe error; the retry rule; and the retention period for a claimed transaction. Protect a claimed transaction from cleanup until its bounded provider attempt completes, or make the callback completion and exchange-code write safely recoverable. Test denial, timeout, provider response loss, expiry during callback, and callback-versus-cleanup races on PostgreSQL. |
| Important change | OpenAPI and Interface handoff | The handoff does not define the concrete mobile client boundary. The existing `@allies/cloud-client` wrapper only exposes cookie-based web `beginSignIn`, `refreshSession`, and `logout`; the mobile provider remains explicitly unavailable. Generated OpenAPI types alone do not say which requests receive a bearer header, which native requests must never receive one, or how the native error codes map to the session state table. This forces INT-008 to invent behavior, contrary to the acceptance criterion. | The plan says the Interface will use a generated client and a focused adapter, but gives no client method or header mapping (`auth-002-native-session-contract.md:575-597`). Its handoff check only fetches and generates the schema (`:655-669`). `packages/cloud-client/src/client.ts:189-211` exposes browser-only auth methods and has only a generic `prepareRequest` hook (`:132`, `:177`). `apps/mobile/src/lib/session/session-context.tsx:5-10` remains `native-session-contract-pending`. | Add a versioned consumer-handoff table to the plan and OpenAPI review checklist. Specify the input, output, headers, and retry rule for native begin, exchange, refresh, logout, and bearer account calls. Define an allowlist for bearer injection so public native routes and browser-cookie routes never receive it. Map each documented HTTP/error code to the INT-008 state table, including logout uncertainty and refresh reuse. Require an Interface-owned contract test that compiles this boundary against the pinned schema before INT-008 becomes ready. |
| Important change | Migration and validation claims | The plan claims that fresh and upgraded SQLite and PostgreSQL migrations will pass, but its commands and current CI prove only fresh migration application. They do not create a database at the pre-AUTH-002 migration state, migrate it forward, and verify existing browser families become `browser`. | The migration exit criterion requires fresh and upgrade proof (`auth-002-native-session-contract.md:341-343`, `:531-543`). The listed commands run `migrate` against one current database (`:606-653`). The PostgreSQL CI job says “Apply fresh PostgreSQL migrations” and then runs the marker suite; it has no old-schema upgrade stage (`.github/workflows/ci.yml`, `postgresql-auth` job). | Add a repeatable migration test or CI stage for both SQLite and PostgreSQL: migrate to the last pre-AUTH-002 migration, create representative browser family and refresh rows, apply the new migration, assert `client_kind=browser` and existing refresh rotation still works, then run the native migration checks. State the exact command or test node in the plan. |

AUTH-002 is a Cloud and Interface contract gate; the Nabu epic excludes direct Interface access to Foundry, Hermes, Fly, or runtime services. The inspected Cloud auth, workspace, Makefile, and CI sources contain no such dependency. | Nabu `projects/allies/delivery/epics/EPIC-00.md` says direct Interface access to Foundry, Hermes, Fly, and runtime services is not included. ## Missing Questions

- What exact Railway-proven, non-cookie identity will key the native begin and token-exchange limits?
- What transaction state and retention rule protects a claimed native callback from cleanup while the bounded Google call is in progress?
- What exact browser/native callback settings and Google registrations are valid in each environment?

## Plan Feedback For Revision

- Resolve the Railway native rate-limit identity before approving the threat model or enabling routes.
- Add the provider callback configuration matrix and its negative isolation tests.
- Add a callback transaction state machine, provider-denial behavior, cleanup protection, and PostgreSQL race tests.
- Add a typed Interface consumer-handoff contract for native methods, bearer injection, error mapping, and contract compilation.
- Add forward-upgrade migration proof to CI for SQLite and PostgreSQL.
- Make the HTML artifact clearly map to the Markdown phases.
