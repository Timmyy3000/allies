Gmail v1 · read + send · generic passthrough, Gmail first

Managed Gmail connection: one OAuth, per-Ally grants, short-lived passthrough

Users connect Gmail once through Allies-owned Google OAuth. Each Ally gets an explicit read or send grant. Every execution receives a minutes-long access token and nothing else. The Hermes skill runs unmodified, sends wait for approval, and revocation works at both levels. Calendar stays out of v1 and arrives later as incremental consent.

How a mailbox goes from “connect” to “Ally can read it”

Why this shape

The skill believes it owns a token file; it actually rents it for one execution. That single decision keeps refresh, revoke, and audit in Cloud, keeps Foundry free of OAuth, and makes every later provider the same envelope with a different allowlist.

Locked decisions behind it

  • V1 is Gmail read + send; Himalaya stays a generic-IMAP fallback, never the managed default. D1, D5
  • Plans live as repo Markdown, Cloud leading; Foundry and Interface arrive as follow-up episodes. D2, D9
  • Minimal scopes (gmail.readonly + gmail.send); calendar comes later as incremental consent. D8
  • No new event kind: expiry rides existing states with a reason string. D7

Scope and assumptions

In scope

  • Allies-owned Google OAuth, both entry points, auto-grant to the requesting Ally
  • Per-Ally grants enforced in the Cloud gateway before any Foundry call
  • Access-only mint per execution; opaque injection through existing credential_refs machinery
  • Unmodified Hermes skill; expiry maps to existing states + reason code
  • Approval-gated send; two-level revocation; generic contract for later providers
  • BOUNDARY tests 1–6 pass with 3 watchpoints pinned

Out of scope

  • Google Calendar (reserved; incremental scopes later)
  • Email-arrival triggers; routines stay schedule-only
  • Himalaya as managed default; multi-account fan-out; sync workers
  • New Foundry event kinds, per-provider vaults, Cloud-held attempt state

Load-bearing assumptions

  • Allies-owned verified OAuth client exists before implementation
  • One Gmail account per workspace (second account is a typed conflict)
  • Access TTL ≈ 1h, opaque to Foundry, recorded at mint
  • Foundry continuity gates FND-005–008 remain prerequisites for breadth

Contracts

Conventions: Cloud owns product truth, Foundry owns runtime truth, no shared models. Scope strings stay opaque to the kernel. Tokens never appear in logs.

Representative payloads

OAuth callback (Cloud-internal; tokens never leave Cloud)

{
  "schema_version": "v1",
  "kind": "gmail.oauth_callback",
  "scope": { "kind": "workspace", "cloud_workspace_id": "ws_..." },
  "google": {
    "code": "[redacted: single-use, never logged]",
    "granted_scopes": [
      "https://www.googleapis.com/auth/gmail.readonly",
      "https://www.googleapis.com/auth/gmail.send"
    ]
  },
  "result": "connected | scope_insufficient | already_connected | provider_unavailable"
}

Scope shortfall stores nothing and returns 422: enforced at consent time, not discovered later.

Grant check (gateway-internal; the wire carries only the envelope)

{
  "workspace_id": "ws_...",
  "ally_id": "ally_...",
  "grant": { "level": "read", "grant_generation": 7 },
  "decision": { "allowed": true,
    "tool_allowlist": ["gmail search", "gmail get"],
    "reason_code": null }
}

Dispatch emits the allowlist; the gate denies anything absent from it, so a read-only execution has no send path even though the token carries both scopes.

Execution credential envelope (Cloud to Foundry; provider-neutral)

{
  "schema_version": "v1",
  "kind": "execution.command",
  "command_id": "cmd_...",
  "idempotency_key": "intent_...",
  "scope": { "kind": "workspace", "cloud_workspace_id": "ws_..." },
  "cloud": { "ally_id": "ally_...", "conversation_id": "conversation_...",
             "intent_id": "intent_...", "cloud_binding_id": "binding_..." },
  "credential": {
    "ref": "credref_... (opaque; resolved once at materialization)",
    "expires_at": "2026-09-22T13:00:00Z",
    "tool_allowlist": ["gmail search", "gmail get"],
    "grant_generation": 7
  },
  "payload": { "kind": "execution_input", "text": "..." },
  "fingerprint": "canonical-json-sha256:v1:..."
}

Rules: the ref is expiring and bound to one command — use by another command is rejected, retries of the same command resolve idempotently, each execution mints fresh. It resolves to access-only bytes with no refresh_token; the Cloud outbox holds the ref only, never bytes. Fresh refs change the seed fingerprint and force a rebuild, so stale bytes die with cleanup. The kernel treats expiry and allowlist as opaque; generation mismatch means fenced. Later providers reuse this envelope unchanged.

Approval round-trip for send (existing mirror)

{ "event_type": "approval.requested",
  "payload": { "kind": "approval_request", "approval_id": "018f77d8-...",
    "prompt": "Send to bob@example.com — Subject: Q3 report — [draft preview, ≤16 KiB]" } }
{ "decision": "approve | reject", "approval_id": "018f77d8-...",
  "decided_by": "user_...", "idempotency_key": "approval-choice_..." }
{ "event_type": "execution.terminal",
  "payload": { "kind": "terminal", "status": "succeeded | failed",
    "reason": "sent | rejected_by_user | approval_mismatch | gmail_credential_expired | gmail_send_unconfirmed" } }

Deadlines reuse Foundry constants (30 s acknowledgement, 300 s lifetime, 16 KiB preview cap). Approval binds an immutable normalized payload hash; the gate denies any post-approval field change, and over-cap payloads are never approved. Expiry mid-attempt becomes retryable or repair_required, never a new event kind. Ambiguous sends enter a repair-path confirmation state with automatic replay blocked and a manual Sent check required before any resend.

Injected file (the only secret bytes Hermes ever sees)

{
  "type": "authorized_user",
  "client_id": "<allies-owned client id>",
  "token": "<short-lived access token>",
  "expiry": "2026-09-22T13:00:00Z",
  "scopes": ["https://www.googleapis.com/auth/gmail.readonly",
             "https://www.googleapis.com/auth/gmail.send"]
}

No refresh_token key, no client_secret: the skill's refresh branch is dead by construction and its write-back never fires.

Acceptance (8 checks)

  1. OAuth stores exactly read + send; no Console projects; shortfall returns 422 with nothing stored.
  2. Per-Ally read / send enforced pre-dispatch via the allowlist and at each tool call via the neutral gate; ungranted calls never reach Foundry; read-only executions cannot reach send; revoke fences in-flight.
  3. Per-execution fresh command-bound refs (cross-command reuse rejected, same-command retries idempotent); outbox holds refs, never bytes; refresh, revoke, and audit stay in Cloud; kernel never parses OAuth; injected file has no refresh token; skill checksum proves unmodified.
  4. Expiry maps to existing retryable / repair_required + reason; no new event kind in code or fixtures.
  5. Every send has a prior approval record binding the exact payload hash; over-cap payloads are never approved; decision replay is idempotent.
  6. Both revocation levels proven by test: fenced attempts and scrubbed disconnect.
  7. A second provider reuses the secret table and envelope with zero Foundry changes; calendar absent from v1 consent and allowlists.
  8. BOUNDARY tests 1–6 pass with all three watchpoints pinned and evidenced.
  9. Ambiguous sends enter confirmation state with replay blocked and a manual Sent check before any resend; no exactly-once claims anywhere.
  10. Flag-off disables authorization and credential use including active connections: a true emergency stop.

Validation

Repo checks: Cloud runs make check, make lint, make test APP=<path>; the Foundry slice runs its equivalents in its own episode. Four named end-to-end proofs are required, not optional:

  1. Temp-HERMES_HOME isolation run of Gmail search on an injected access-only token: refresh branch dead, no token rewrite.
  2. Duplicate-send regression: forced post-delivery fault still delivers exactly once.
  3. Machine-replacement continuity: new volume plus same binding re-materializes and works with no user action.
  4. Revocation at both levels: grant delete fences the attempt; disconnect deletes refresh, revokes at Google, scrubs files, and later attempts fail closed.

Unit and API coverage wraps the grant matrix, reason codes, envelope redaction, generation fencing, scope-shortfall rejection, PKCE and state validation, and idempotent connect, approval, and dispatch replay. A checksum guard keeps the Hermes skill byte-identical.

Boundary proof

Three watchpoints stay pinned through implementation: grant logic lives only in the Cloud gateway; Cloud persists no attempt or session state for credentials (minting is stateless per execution); scope strings never enter kernel parsing. Evidence is by code location, grep, and test in Phase 6.

Placement summary: vault, consent, and grants are product truth in the driving cloud; the passthrough envelope is the versioned, cloud-agnostic contract; the kernel handles opaque bytes, approval mirror state, and execution fencing. On-prem consumers implement the same envelope against their own vault with identical kernel behavior.
