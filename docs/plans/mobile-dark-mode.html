Mobile dark mode

Make the current Allies mobile experience follow the device light or dark mode while preserving selected Ally accent colors.

Feature overview

  • Problem: Current mobile screens use fixed light colors.
  • Target users: Allies mobile users who use light or dark device mode.
  • Source docs: docs/superpowers/specs/2026-09-03-mobile-dark-mode-design.md, ENGINEERING_STYLE.md, and Allies mobile notes in Nabu.
  • Success outcome: All current mobile routes keep their hierarchy and selected Ally accents while specified surfaces, text, controls, and status-bar icons follow the device mode.

User stories

  1. As a mobile user, I want the app to follow my device appearance, so that it feels consistent with the rest of my device.
  2. As a mobile user, I want active actions to retain the selected Ally color, so that color selection still has meaning in dark mode.
  3. As a maintainer, I want shared semantic theme tokens, so that future screens do not add separate light and dark color branches.

Before coding, capture the complete porcelain status, including untracked files, in a local uncommitted review note. Record hashes or diffs for pre-existing out-of-scope tracked files, then compare both snapshots after implementation.

Scope

In scope

  • Extend the existing Colors and useTheme boundary.
  • Apply the theme to current mobile routes and shared UI.
  • Keep enabled buttons on the selected Ally accent.
  • Use #202020 for disabled or otherwise inactive button backgrounds in dark mode.
  • Theme onboarding inputs, chat composers, modal surfaces, text, controls, and monochrome icons.
  • Make the root status bar follow device mode.
  • Add a small theme contract test and update affected behavior tests.

Out of scope

  • Manual theme selection, new providers, styling libraries, or dependencies.
  • Changes to artwork, Ally colors, logos, provider logos, navigation, authentication, persistence, APIs, or splash artwork.
  • Restoring routes deleted by parallel work or editing unrelated dirty files.

Theme contract

The existing theme modules remain the only theme boundary. Add semantic tokens and a small getTheme(scheme) resolver. Dark selects only when the scheme is dark; all other values use light. The existing reactive React Native hook provides live device updates.

Component behavior

  • PrimaryButton keeps its animated accent behavior. Every enabled action uses the selected Ally color; disabled actions use the themed inactive surface.
  • The shared bottom sheet uses the modal surface token.
  • Back, search, settings, and modal-close icons use the active theme without duplicate assets.
  • One root status bar uses light icons in dark mode and dark icons in light mode.
  • No manual toggle or new dependency is added.

Implementation phases

Phase 1: Theme contract and shared controls

  • Extend Colors, add getTheme, and keep useTheme reactive.
  • Make the root status bar dynamic.
  • Update PrimaryButton, the bottom sheet, and onboarding progress.
  • Add the exact token contract test and update affected button/layout tests.

Exit criteria: Token and button tests pass and no screen-level fixed status bar remains.

Phase 2: Apply tokens to current screens

  • Theme welcome, onboarding shell/header/name/look/job/personality, preview, post-setup, Allies list, sign-in, missing-Ally, and mock conversation screens.
  • Pass the current accent into OnboardingAlliesScreen; keep orange as its default when no selected Ally color exists.
  • Theme back, search, settings, and modal X icon colors through the existing image/SVG paths.
  • Preserve Ally accents for active buttons, progress, links, swatches, send controls, and personality controls.
  • Pass the selected Ally accent to the enabled “I’ll do this later” action.

Exit criteria: All current routes render with equivalent light-mode hierarchy and the specified dark-mode values.

Acceptance criteria

  1. Device light and dark changes update the current screen; unspecified mode uses light.
  2. Dark backgrounds, inputs, modal, button, text, and icon colors match the approved values.
  3. Selected Ally colors continue to own every enabled action; orange remains the default.
  4. #202020 is used only for inactive or disabled button backgrounds.
  5. One root status bar uses the correct icon color for each mode.
  6. Supporting grey text and account-modal fine print remain unchanged.
  7. Existing artwork, logos, provider logos, and navigation behavior remain unchanged.
  8. Targeted tests, full tests, typecheck, lint, bundle/export, and git diff --check pass.

Test plan

  • Unit: exact theme tokens, unspecified fallback, selected accent preservation, inactive button colors, and existing layout behavior.
  • Regression: existing onboarding, preview, mock, modal, and cloud-client tests.
  • Manual: review every current route in both device modes, change mode while mounted, select a non-orange Ally color, inspect disabled/inactive buttons, and inspect the modal X/privacy treatment.

Risks and mitigations

  • Fixed screen status bars could override the root: remove them and keep one owner.
  • Active Ally colors could be replaced by generic dark colors: preserve accentColor for every enabled action and test a non-orange accent.
  • Parallel dirty edits could be overwritten: patch current files in place and inspect exact paths.
  • SVG tinting could vary by platform: require runtime checks of every tinted icon on an Android emulator/device and an iOS simulator/device, and isolate any fallback to a small inline react-native-svg icon with a color prop.
  • Supporting grey text could be too weak on black: review both themes and keep primary copy white.
  • Unapproved dirty-worktree paths could be included: record the complete git status --porcelain=v1 --untracked-files=all snapshot, preserve hashes or diffs for pre-existing out-of-scope tracked files, compare both after implementation, and stage exact files or hunks.

Rollback is limited to the focused theme changes. No persisted data or native schema changes are made.
