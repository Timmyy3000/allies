# Beta labels and visibility

Route: fast. Status: Accepted for labels implementation under the fast-route user authorization and reviewed adversarial/simplicity dispositions. HTML required: no. This slice has no deletion or retention dependency.

## Scope and evidence

Generate a 2-3 word label from the job at new ally creation, preserve explicit roles such as `chief of staff`, allow editing in a minimal web Ally Settings surface, and persist a per-ally Show label checkbox defaulting false. Render enabled nonempty labels beneath the ally name. Name/job/personality edits, general Account redesign, native settings UI, deletion, and historical generation backfill are outside this slice.

Inspected all three repository AGENTS/engineering policies, Interface README/package scripts/CI/template, Cloud README/Makefile/CI, Cloud `backend/allies/models.py`, `services/creation.py`, API schemas/controllers and `backend/activities/services/approval_explanations.py`; Interface `packages/cloud-client/src/mappers/allies.ts`, Home and query code. Orchestrator inspected current header: settings leads to Account; no Ally Settings route exists. Nabu baseline: Cloud owns product truth and web calls Cloud only. Use existing Cloud capability/origin/session controls.

## Implementation

1. Cloud: add Ally fields `label` (empty default, 80 chars), `show_label` (false), `settings_revision` (0), and `label_generation_state` (`pending | claimed | complete | unavailable`). Existing rows migrate to unavailable/empty/false; new creation explicitly sets pending. Do not call a provider from migrations or reads. Keep existing creation fingerprints and Foundry seeds unchanged.
2. Add a focused `backend/allies/services/labels.py` and task. After creation commits, enqueue generation; a bounded pending scan in the existing beat/task pattern recovers broker failure. Lock and move pending to claimed before provider I/O. Only the first claim calls Luna. Use the existing Responses pattern: `gpt-5.6-luna`, reasoning none, store false, strict JSON `{ "label": "chief of staff" }`, job-only source, no redirects, 5-second socket/6-second total deadline, 32 KiB response byte cap, 100 output tokens, no automatic provider retry. Use the existing ALLIES_WAITLIST_OPENAI_API_KEY credential; missing credential means unavailable without network I/O. Use auths.throttle.check_rate_limit under a label-specific scope: 6 calls/workspace and 30 global per 60 seconds; throttle/cache outage fails closed to unavailable. Bound concurrent provider calls to four globally with existing cache-slot conventions (7-second TTL); pending batch remains at most 100 rows/60 seconds. Log only fixed operation label, generated/unavailable outcome, elapsed time and safe reason (credential_missing, budget_exhausted, budget_unavailable, timeout, invalid_output, provider_error). Never log job/name/label/provider body. Validate 2-3 whitespace-separated words, <=80 characters, no control characters/newlines. The prompt must preserve explicitly supplied role titles, including chief of staff, rather than generalizing them. Keep LLM determination for job prose; do not add a heuristic role extractor or claim perfect semantic accuracy. Test the prompt contract and representative title outputs, including chief of staff. Use one Luna generation path even when the entire job is already a short role title; do not add a whole-job passthrough. On malformed/refused/timeout output leave empty/unavailable without failing ally creation. The bounded recovery scan includes pending rows and claimed rows with updated_at older than 120 seconds; it changes stale claimed rows to unavailable without issuing another potentially billed request. Set updated_at explicitly when claiming. Reuse this timestamp because identical saves are no-ops and initial generation has an empty label with visibility forced false; only a changed label can interrupt that claim. Generation completion/failure is conditional on claimed state and captured revision. A late provider result after stale recovery cannot persist.
3. Add `PATCH /api/v1/workspaces/{workspace_id}/allies/{ally_id}/settings` using existing response envelope. Request: `{ "label": "chief of staff", "show_label": true, "settings_revision": 0 }`. Require authenticated workspace owner `PROFILE_WRITE`, correct ancestry, browser origin/CSRF (existing native policy if supported), strict types and no extra keys. Manual label is empty or 2-3 words under the same bound; an empty label requires show_label false on the server. Lock Ally and reject stale revision with 409. An identical payload against the current revision succeeds as a no-op: no revision increment, timestamp update, or generation-state change. A changed label ends generation ownership; a changed visibility value alone preserves it. Persist actual changes and increment revision. Generator completion uses conditional update against claimed state and captured revision and atomically increments settings_revision on a successful label write. Thus an edit wins against a delayed generator, and a stale form opened before generation receives 409 instead of erasing the generated label. During initial generation the label is empty, so visibility must remain false and visibility-only edits cannot interrupt that claim. Return updated Ally with appended `label`, `show_label`, `settings_revision`; 401/404/409/422 follow existing errors. Repeated stale save reconciles, never overwrites silently.
4. Shared client: extend Zod mapper, view model and client method in `packages/cloud-client`; regenerate local Cloud OpenAPI snapshot/types using existing fetch/generate/verify scripts. Missing fields on old responses default to empty/false/0; unsupported settings endpoint reports an error, not a local-only save. Update `apps/web/lib/allies/queries.ts` and Home cache invalidation.
5. Web: add a focused settings dialog/sheet near Home, entered from the selected ally header on desktop and mobile web. Keep Account separately accessible. Include label input, Show label checkbox and Save only for this slice. Disable Show label when the draft label is empty and set its draft value false when the label is cleared. Preserve draft on save failure or revision conflict; prevent duplicate saves; announce persistence success. Use current dark tokens, existing header icon/button conventions and responsive layout. Render the label in home-workspace.tsx AllyRow beneath its name only when true and nonempty; never substitute raw job. Preserve the existing chat job subtitle and provisioning/status copy. This slice changes roster label presentation, not the conversation header job contract. Include keyboard focus containment/restoration, associated input labels, Escape/cancel, and accessible error/status text. Long labels must not break roster layout. Refresh/refetch cannot overwrite a dirty draft.

## Acceptance and validation

- Creation retry and duplicate task produce one automatic provider attempt; generation failure still creates ally; delayed generation never replaces user edit. Prompt/output fixtures cover `chief of staff` preservation without claiming an LLM semantic guarantee. Test a form opened before generation: generator increments revision, stale save gets 409 and cannot erase the label. Test claimed rows older than 120 seconds recover unavailable and reject late output.
- New/existing labels start hidden; toggle/edit/save/reload is durable and scoped to one ally. Empty label renders nothing and cannot have show_label true. Test that an identical save during a generation claim leaves the revision, updated_at and claim unchanged; test that changed label text terminates the claim, while visibility-only changes increment revision without changing generation state. Invalid label, CSRF failure, wrong workspace, unauthorized capability and stale revision have no mutation.

## Risks, decisions and rollout

One persisted claim intentionally favors no repeated billing over retrying a rare crashed generation; the user can edit an empty label. Existing allies receive no generation backfill because the requirement says at creation. If automatic retry/backfill is later requested, it needs a separate bounded cost/idempotency decision.

Keep generation outside DB locks. Reuse provider request conventions without coupling label generation to approval business logic or introducing a generic AI framework. Cap pending task batches at 100 records/60 seconds and use existing task scheduling. Existing settings requests should cancel/update only the selected ally's queries.

Deliver coherent Cloud and Interface PRs with migration/contracts/tests; Cloud goes first, web second. Preserve additive columns on rollback; disable generation/hide UI if needed. No merge, deployment, or live destructive testing is authorized. Enkii v1.3.0 workflow updates are an independently verified task-wide change, not a dependency of label behavior.
