Mobile post-onboarding notifications and Allies home

Restore the notification prompt, request native permission, and continue into a lightweight Allies roster using the completed Ally already held by onboarding.

Platform
Expo SDK 57 / React Native
Native boundary
OS notification permission
Data boundary
Flow-local single Ally

Core constraint: the native permission request is real, but push delivery, token registration, Cloud roster loading, and durable mock catalogs remain out of scope.

Feature overview

  • Restore the notification card to its static approved skeleton bars.
  • Use expo-notifications to request OS permission from Allow notifications.
  • Continue after Allow or I’ll do this later into a finished-looking Allies home.
  • Show the selected Ally from the existing onboarding state and let Make an ally restart local creation.

Flow contract

Implementation phases

1. Restore the visual and state contract

Add the allies state and transition assertions. Replace the notification block shimmer with static #D9D9D9 bars while preserving the established card, copy, and button measurements.

2. Add the native permission boundary

Install the Expo SDK 57 compatible notifications package, configure its plugin, create the Android channel before the request, and always continue after the request attempt.

3. Add the Allies roster

Build the roster from the existing flow-owned Ally. Reuse OnboardingAllyPreview and PrimaryButton; normalize and bound the greeting preview; keep search and account controls visual until their product contracts exist.

4. Validate

Run focused onboarding tests, mobile lint, mobile typecheck, Expo config validation, and git diff --check. Test the OS prompt only with a rebuilt native binary containing the module.

Acceptance criteria

  1. The notification card matches the approved static visual and has no dominant shimmer overlay.
  2. Allow notifications calls the native permission API and prepares an Android channel when required.
  3. I’ll do this later does not request permission.
  4. Granted, denied, and failed permission attempts all reach the Allies roster.
  5. The roster shows the completed Ally’s color, shape, name, bounded greeting preview, presence, time, and Make an ally action.
  6. Make an ally resets the local flow without adding a second data model.
  7. No push token, network request, password, or durable fake catalog is introduced.

Boundaries and risks

Cloud remains the owner of durable Allies and notification preferences. The local row is a temporary display of the Ally completed in this flow. Adding expo-notifications is a native dependency change, so an OTA cannot add it to an already installed binary; build a compatible binary before device testing.
